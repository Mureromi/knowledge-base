## 三、对关键实现的审查结论

### 3.1 ★ 并发冒烟测试是**真测试**，不是空泛断言

这是我最担心被写成"假测试"的一条（阶段 2 我就发现自己写过一条假测试）。审查结果：**写法正确**。

```python
def slow_extract(raw, source_type, max_pages):
    time.sleep(0.3)                    # 纯同步 sleep，放大差异
monkeypatch.setattr("app.worker.extract_text", slow_extract)

await asyncio.gather(process_document(...), process_document(...))
assert elapsed < 0.5                   # to_thread → 0.3s；漏了 → 串行 0.6s
```

**非空泛性论证**：若 `worker.py` 漏掉 `await asyncio.to_thread(...)`（直接同步调用），第一个 `time.sleep(0.3)` 会独占事件循环，第二个只能在它结束后开始，总耗时必然 ≥ 0.6s，断言失败。**桩函数签名 `(raw, source_type, max_pages)` 与真实 `extract_text` 完全一致**（已核对 `app/services/parsing.py:100`），确保 patch 真正生效而非误打。

### 3.2 ★ 确定性失败的处理是**正确的**

```python
except (EmptyDocumentError, UnsupportedDocumentError) as exc:
    # 置 failed 后 return，不 raise
    return f"failed: {type(exc).__name__}"
except Exception as exc:
    raise TransientError(str(exc))     # 只有未知异常才交给 ARQ 重试
```

实测验证：扫描件 worker 日志中 **retry 出现 0 次**。这个区分（确定性失败 vs 瞬时故障）是异步任务最容易做错的地方，实现正确。

### 3.3 ★ `replace_chunks` 幂等设计到位

`crud/document.py` 有独立的 `replace_chunks`（先删后写），而非直接 `create_with_chunks`。实测重复执行任务后 `chunks` 未从 1 变成 2。这防住了"重试导致重复切片 → 检索出重复引用 `[1][1][1]`"的问题。

### 3.4 事务边界正确（阶段 2 的教训被吸收了）

worker 里"读任务+置 running → commit → **事务外**做 CPU 解析 → 新事务写结果"。没有把耗时解析关在事务里，不会长时间占用连接。

## 五、三条观察 → 已全部修复（2026-10-13）

### 5.1 `processing` 状态实际观测不到 —— ✅ 已修复（这是真 bug，不只是时序）

> **修复**：worker 在置任务 `running` 时**漏了同步更新 `documents.status`**——这才是根因（不是轮询太快）。已补 `set_status(..., "processing")`，与 `mark_running` 同事务提交。
> **回归测试**：`test_phase3_fixes.py::test_document_status_is_processing_while_parsing`
> （用桩函数在**解析发生的那一刻**回查数据库，避开轮询时序问题）

> **修复后的实测（诚实记录）**：真实环境用 **20ms 高频轮询**仍未捕获到 `processing`——
> 因为一个 1 页 PDF 的解析只要 1ms，中间态存活时间短于任何轮询间隔。
> 所以修复的**真实收益**是：对**大文件**（几百页、耗时数百毫秒以上）用户能看到「解析中」；
> 小文件不管修不修都看不到，这是物理限制而非缺陷。
> **不要试图通过"加人工延迟"让它可见**——那是为了让演示好看而牺牲性能，方向错了。
> 前端若要精确显示进度，应当依据 `started_at` 是否存在 + `task_status`，而不是死等 `status == "processing"`。

**验收时的原始判断（已被后续排查修正）**：当时以为是"解析太快所以看不到"，属于物理限制。

**修正后的结论**：其中**有一半是真 bug** —— worker 压根没同步 `documents.status`，所以**连大文件也不会显示 processing**。只有「小文件抓不到」是物理限制，而「大文件也看不到」是实现漏了一行。这正是验收的价值：**表面现象相同，根因却完全不同。**

### 5.2 任务历史随文档删除而级联消失 —— ✅ 已修复

> **修复**：外键 `CASCADE` → `SET NULL` + `document_id` 可空，并显式在 `delete_document` 里置空；迁移 `bcc942ff68e3` 已在 PostgreSQL 应用并验证（`delete_rule = SET NULL`）。
> **回归测试**：`test_phase3_fixes.py::test_task_history_survives_document_delete`

`processing_tasks.document_id` 是 `ondelete="CASCADE"`。实测删除文档后，其任务记录（含失败原因）一并消失。

**取舍说明**：文档 §4.2 说建这张表是为了"可追溯重试历史"和"统计失败率"。但级联删除意味着**文档一旦被删，其历史也随之消失**——想做长期失败率统计的话，这块数据会缺口。若将来需要，可改为 `SET NULL` 并保留任务记录（`chat_logs.session_id` 用的就是这个策略）。

### 5.3 僵死任务重投时有窄窗口的重复执行可能 —— ✅ 已修复

> **修复**：新增 `claim_stale_running`，用**条件 UPDATE + RETURNING 原子抢占**——只有"此刻仍是 running 且确实超时"的行会被更新，并精确返回抢到的 id 列表；`cleanup_stale_tasks` 只对这批 id 重投（不再用条数切片对账）。
> **回归测试**：`test_phase3_fixes.py::test_claim_stale_running_returns_claimed_ids`（含"未超时的不被误抢"与"重复调用不重复抢"两条断言）

`cleanup_stale_tasks` 先查 stale id 列表、再重置、再重新投递。理论上存在：任务实际上仍在运行（尚未真正僵死，只是慢），被重置为 `pending` 并重投 → 两个 worker 同时解析同一文档。

**风险评估：低**。后果是浪费 CPU + 可能触发一个数据库写入冲突（被 `TransientError` 捕获重试），不会产生错误数据（`replace_chunks` 是幂等的先删后写）。且 `task_stale_seconds` 默认 600s，正常运行几乎不会命中。
