## 1. ★★ 最重要的实测结论：评测框架会**静默失效**

这是本阶段第一个、也是最重要的发现。**如果跳过这一步，你后面所有"效果提升 X%"的结论都建立在错误的尺子上。**

### 1.1 发现过程

我按"主流做法"先试了 DeepEval 的忠实度（Faithfulness）指标，用**你的 DeepSeek 做裁判**，然后拿**我已知答案的用例**去测它——包括明显的幻觉：

| 用例 | 上下文依据 | DeepEval 忠实度 | **应该是什么** |
| --- | --- | --- | --- |
| 好答案（"5-7 个工作日退回"） | ✅ 有依据 | 1.00 通过 | ✅ 对 |
| **完全无关**（"巴黎是法国首都"） | ❌ 无任何依据 | **1.00 通过** | ❌ **错** |
| 直接矛盾（"30 天 + 5% 手续费"） | ❌ 与资料矛盾 | 0.50 未通过 | ✅ 对 |
| **部分编造**（"20 元提现费"） | ❌ 资料未提 | **1.00 通过** | ❌ **错** |

**判对 1/4。** 一条完全无关的回答被评为"完全忠实"。

### 1.2 根因不是模型能力

我直连裁判模型，用同一组数据问它一个朴素问题：

```
上下文：审核通过后，款项将在 5-7 个工作日退回原支付渠道。
回答：退款需要 30 天才能到账，并且要收 5% 手续费。
这个回答是否忠于上下文？
→ 模型答："否，上下文说明 5-7 个工作日退回原支付渠道，未提及 30 天到账和 5% 手续费。"
```

**模型完全有能力判断。** 问题出在 DeepEval 的指标提示词把任务**分解**成若干步骤（拆解陈述 → 逐条验证 → 加权），这套分解在**短上下文 + 单条事实**的 RAG 场景下会失效——它倾向于"没找到矛盾就算忠实"，而**忽略了"没有任何依据"也是一种不忠实**。

### 1.3 自写 judge prompt 的有效性（实测 4/4）

同一组用例，换成我自己写的 judge：

```python
PROMPT = """你是严格的 RAG 答案校验员。判断【回答】是否完全由【参考资料】支撑。
规则：回答中任何参考资料没有的事实/数字/条件都算不忠实；与资料矛盾也算不忠实。
输出 JSON 对象：{{"faithful": <布尔>}} 表示是否有依据，另加 "reason" 一句话。
示例：{{"faithful": false, "reason": "30 天到账在资料中无依据"}}

【参考资料】
{ctx}

【回答】
{out}"""
```

| 用例 | 自写 judge | 理由（模型给出） |
| --- | --- | --- |
| 好答案 | ✅ True | 回答与参考资料完全一致 |
| 完全无关 | ✅ False | 关于巴黎的内容在参考资料中完全没有依据 |
| 直接矛盾 | ✅ False | 30 天到账和 5% 手续费均无依据且与资料矛盾 |
| 部分编造 | ✅ False | 20 元提现费在资料中无依据 |

**4/4，且理由可读。**

### 1.4 三条结论（本阶段的核心价值）

1. **评测框架必须先用"已知坏答案"验证，才能拿它去测量。** 就像阶段 4 的 rerank 评测一样——**先证明尺子是准的**。
2. **`ragas` 在本机甚至装不上**（`langchain_community` 已移除 `chat_models.vertexai`，而 ragas 仍引用它）——所以"用主流框架"这条路本身就不通。
3. **裁判模型够用的前提下，自写 prompt 更可控**：逻辑透明、提示词能针对你的数据分布调优、零依赖、出问题能直接读 prompt 定位。

> **本阶段最重要的一句话**：一个未经验证的评测指标比没有评测更危险——**它会给你虚假的信心**。这和阶段 3/4 发现的"假通过测试"是同一类问题的不同表现。

## 2. ★ 一个容易踩的 Python 陷阱（我踩了两次）

写 judge prompt 时，**如果 prompt 用 `str.format()` 插值，而里面又含 JSON 示例，大括号必须转义**：

```python
# ❌ 会抛 KeyError: '"faithful"'
PROMPT = """输出 JSON：{"faithful": <布尔>} ...
【资料】{ctx}
【回答】{out}"""
PROMPT.format(ctx=..., out=...)      # .format() 把 {"faithful": ...} 当占位符

# ✅ 转义大括号
PROMPT = """输出 JSON：{{"faithful": <布尔>}} ...
【资料】{ctx}
【回答】{out}"""
```

**排查提示**：如果报 `KeyError: '"faithful"'`（键名带引号），**100% 是这个原因**，不是模型或 JSON 的问题。我当时误以为是模型输出格式错误，绕了两轮才定位。

**更稳的做法**：干脆不用 `.format()`，改成 `PROMPT.replace("{ctx}", ctx)`，从根上避开。

> 顺带一个同源提示：prompt 里**不要写 `true/false` 这种占位符**（模型会照抄成字面量）。要给**示例值**（`"faithful": false`）。

## 3. 可观测性：Langfuse Cloud

### 3.1 为什么需要它（现有日志不够在哪）

阶段 4 补的 JSON 日志已经能回答"花了多少钱""有没有命中缓存"，但回答不了**一次问答内部的分解**：

| 问题 | 现有日志 | Langfuse |
| --- | --- | --- |
| 本次问答总耗时/成本 | ✅ | ✅ |
| **改写用了多久、检索用了多久、LLM 用了多久** | ❌ 只有总数 | ✅ 分 span |
| **哪几个切片被召回、各自什么分数** | ❌ 只在 citations 里（接口可见，日志没有） | ✅ 作为 span 的 metadata |
| 某次问答的完整输入输出 | ❌ | ✅ 可回放 |
| 一批评测的历史对比 | ❌ | ✅ dataset run |

### 3.2 接入方式（已核实 langfuse 4.17.0）

```python
# app/clients/tracing.py
"""Langfuse 追踪封装。

★ 与既有基础设施的关系：
  - 结构化日志（阶段 4）负责"机器可读的运行事件"，是**必选**的
  - Langfuse 负责"一次问答的内部拆解与可视化"，是**可选增强**
  两者互补，不互相替代。LANGFUSE_ENABLED=false 时所有 trace 调用退化为 no-op。

★ 隐私边界（必须明确）：开启后，**用户问题、检索到的切片内容、模型回答**都会发往
  Langfuse Cloud。个人知识库自用可以接受；**若文档含敏感内容，必须改用自托管**。
"""

import logging
from contextlib import contextmanager
from typing import Any

from app.core.config import settings

logger = logging.getLogger(__name__)

_client = None


def startup() -> None:
    """在 lifespan 里调用。未配置 key 或未启用时留空，后续调用自动 no-op。"""
    global _client
    if not settings.langfuse_enabled:
        logger.info("Langfuse 未启用（LANGFUSE_ENABLED=false），追踪退化为 no-op")
        return
    if not (settings.langfuse_public_key and settings.langfuse_secret_key):
        logger.warning("Langfuse 已启用但缺少 key，追踪退化为 no-op")
        return
    from langfuse import Langfuse

    _client = Langfuse(
        public_key=settings.langfuse_public_key,
        secret_key=settings.langfuse_secret_key,
        host=settings.langfuse_host,
    )
    # ★ auth_check() 能在启动时就发现 key 配错，而不是等到第一次问答才发现
    try:
        if _client.auth_check():
            logger.info("Langfuse 已连接: %s", settings.langfuse_host)
        else:
            logger.error("Langfuse 鉴权失败（key 或 host 不对），追踪退化为 no-op")
            _client = None
    except Exception as exc:                     # noqa: BLE001
        logger.error("Langfuse 连接失败，追踪退化为 no-op: %s", exc)
        _client = None


def shutdown() -> None:
    """★ 必须调用：Langfuse 是异步批量上报，不 flush 会丢掉最后的 trace。"""
    global _client
    if _client is not None:
        try:
            _client.flush()
        except Exception as exc:                 # noqa: BLE001
            logger.warning("Langfuse flush 失败: %s", exc)
        _client = None


@contextmanager
def trace_span(name: str, **metadata: Any):
    """记录一个 span。未启用时是纯粹的 no-op（几乎零开销）。"""
    if _client is None:
        yield None
        return
    with _client.start_as_current_span(name=name) as span:
        if metadata:
            span.update(metadata=metadata)
        yield span
```

### 3.3 ★ `flush()` 是最容易漏的一步

Langfuse 客户端**异步批量上报**。如果进程退出前不 `flush()`：

- **web 进程**：最后几次问答的 trace 直接丢失
- **worker 进程**：**整个 worker 的 trace 全丢**——因为 worker 长期运行、退出时才上报

**所以 `shutdown()` 里必须 `flush()`，并且 web 与 worker 都要调。** 这个坑在自托管/云上表现一样，与网络无关。

### 3.4 埋点位置（对应阶段 4 的流水线）

```
trace: chat
├── span: query_rewrite      （改写耗时；metadata: 原文 → 改写句）
├── span: retrieval
│   ├── metadata: 关键词候选 chunk_ids、向量候选 chunk_ids
│   ├── metadata: RRF 融合后的顺序
│   └── metadata: rerank 是否启用、rerank 后的顺序
├── generation: llm_call     （prompt/completion、tokens、cost、latency）
└── span: cache_lookup       （命中与否、命中时省下的成本）
```

**关键点：`retrieval` span 要记录"改了顺序"这件事**。阶段 4 的 `RetrievalChunk` 已经有 `keyword_rank` / `vector_rank` 字段——把它们写进 span metadata，就能在 Langfuse 里直观看出"某次 rerank 把哪条从 #3 提到了 #1"。**这是排查检索质量最有力的工具。**

## 4. 评测体系

### 4.1 两类指标必须分清

| 类型 | 衡量什么 | 用什么 | 是否需要 judge |
| --- | --- | --- | --- |
| **检索指标** | 该召回的切片有没有被召回、排第几 | 规则计算（纯代码） | ❌ 不需要 |
| **生成指标** | 答案是否忠于资料、是否切题 | LLM judge | ✅ 需要 |

**为什么必须分开**：RAG 效果差有两种完全不同的原因——**召回不到**（检索问题）vs **召回到了但答歪**（生成问题）。混在一起看"总分"，你无法判断该优化哪一环。阶段 4 的 rerank 评测就是典型的"只看检索"。

### 4.2 检索指标（规则计算，零成本）

```python
# app/evals/metrics_retrieval.py
"""检索指标：纯规则计算，不需要 LLM，可高频跑。"""


def hit_at_k(ranked_doc_ids: list[int], expected_doc_ids: set[int], k: int) -> bool:
    """Top-k 里是否命中任一期望文档。"""
    return bool(set(ranked_doc_ids[:k]) & expected_doc_ids)


def recall_at_k(ranked_doc_ids: list[int], expected_doc_ids: set[int], k: int) -> float:
    """Top-k 覆盖了多少比例的期望文档（期望多条时比 hit 更细）。"""
    if not expected_doc_ids:
        return 0.0
    return len(set(ranked_doc_ids[:k]) & expected_doc_ids) / len(expected_doc_ids)


def reciprocal_rank(ranked_doc_ids: list[int], expected_doc_ids: set[int]) -> float:
    """第一个命中位置的倒数（MRR 的单项）。衡量"排多靠前"，比 hit 更能反映排序质量。

    ★ 这个指标是 rerank 的专用尺子：rerank 不改变召回集合，只改变**名次**，
      所以 hit@5 对它不敏感（阶段 4 实测正是 +0%），而 MRR 能反映出来。
    """
    for i, doc_id in enumerate(ranked_doc_ids, start=1):
        if doc_id in expected_doc_ids:
            return 1.0 / i
    return 0.0
```

> **`reciprocal_rank` 的重要性**：阶段 4 的 rerank 评测只看了 hit@1 和 hit@5，得出"+6% / +0%"。如果当时有 MRR，就能更精确地量化"rerank 把正确答案提前了多少名"——**这比 hit@1 更有说服力**。这是本阶段对阶段 4 方法论的一个补强。

### 4.3 生成指标（自写 LLM judge）

```python
# app/evals/judge.py
"""LLM judge：用 DeepSeek 自己当裁判（复用现有 key，不引入新厂商）。

★ 未经"已知坏答案"验证的指标不能用（§1）。所以本模块自带一个自检函数
  `validate_judge()`：用 4 个已知答案（2 好 2 坏）跑一遍，判对率 < 1.0 就报错。
  这是保证"尺子是准的"的自动化手段——把 §1.1 的人工发现变成一条可重复执行的检查。
"""

import json
import logging

from openai import AsyncOpenAI

from app.core.config import settings

logger = logging.getLogger(__name__)

# ★ 大括号已转义（§2）；不要写 true/false 占位符，要给示例值
FAITHFULNESS_PROMPT = """你是严格的 RAG 答案校验员。判断【回答】是否完全由【参考资料】支撑。

规则：
1. 回答中任何参考资料里没有的事实、数字、条件、承诺，都算不忠实。
2. 回答与参考资料矛盾，算不忠实。
3. 只做判断，不要自行补充知识。
4. 输出 JSON 对象，含两个字段：
   - "faithful"：布尔值
   - "reason"：一句话说明

示例输出：{{"faithful": false, "reason": "回答提到的 30 天到账在资料中无依据"}}

【参考资料】
{ctx}

【回答】
{out}"""

COMPLETENESS_PROMPT = """你是严格的 RAG 答案校验员。判断【回答】是否**完整覆盖**了【要点】。

规则：
1. 逐条核对【要点】是否在【回答】中体现（同义表述也算）。
2. 输出 JSON 对象：
   - "covered"：被覆盖的要点编号列表（从 1 开始）
   - "missing"：未被覆盖的要点编号列表
   - "reason"：一句话说明

示例输出：{{"covered": [1], "missing": [2], "reason": "第 2 点未提及"}}

【要点】
{points}

【回答】
{out}"""


class Judge:
    def __init__(self) -> None:
        self._client = AsyncOpenAI(
            api_key=settings.llm_api_key,
            base_url=settings.llm_base_url,
            timeout=60.0,
        )
        self.calls = 0            # 便于统计评测成本

    async def _ask_json(self, prompt: str) -> dict:
        self.calls += 1
        resp = await self._client.chat.completions.create(
            model=settings.llm_model,
            messages=[{"role": "user", "content": prompt}],
            temperature=0.0,                       # ★ 评测必须确定性
            max_tokens=500,
            response_format={"type": "json_object"},
            extra_body={"thinking": {"type": "disabled"}},   # ★ 评测不需要思考模式（省 75% 成本）
        )
        return json.loads(resp.choices[0].message.content)

    async def faithfulness(self, answer: str, contexts: list[str]) -> dict:
        """答案是否有资料支撑。返回 {"score": 0/1, "reason": str}。"""
        prompt = FAITHFULNESS_PROMPT.replace("{ctx}", "\n".join(contexts)).replace("{out}", answer)
        data = await self._ask_json(prompt)
        return {"score": 1.0 if data.get("faithful") else 0.0, "reason": data.get("reason", "")}

    async def completeness(self, answer: str, points: list[str]) -> dict:
        """是否覆盖了标注的要点。返回 {"score": 0~1, "missing": [...]}。"""
        numbered = "\n".join(f"{i}. {p}" for i, p in enumerate(points, start=1))
        prompt = COMPLETENESS_PROMPT.replace("{points}", numbered).replace("{out}", answer)
        data = await self._ask_json(prompt)
        covered = len(data.get("covered") or [])
        total = max(len(points), 1)
        return {
            "score": covered / total,
            "missing": [points[i - 1] for i in (data.get("missing") or []) if 1 <= i <= len(points)],
            "reason": data.get("reason", ""),
        }


# ---------------------------------------------------------------------------
# 自检：把 §1.1 的人工发现变成可重复执行的检查
# ---------------------------------------------------------------------------
SELF_CHECK_CASES = [
    # (答案, 资料, 期望是否忠实)
    ("审核通过后，款项将在 5-7 个工作日退回原支付渠道。",
     ["审核通过后，款项将在 5-7 个工作日退回原支付渠道。"], True),
    ("巴黎是法国首都，人口约 214 万。",
     ["审核通过后，款项将在 5-7 个工作日退回原支付渠道。"], False),
    ("退款需要 30 天才能到账，并且要收 5% 手续费。",
     ["审核通过后，款项将在 5-7 个工作日退回原支付渠道。"], False),
    ("审核通过后 5-7 个工作日到账，另外需要支付 20 元提现费。",
     ["审核通过后，款项将在 5-7 个工作日退回原支付渠道。"], False),
]


async def validate_judge(judge: Judge) -> float:
    """★ 用已知答案验证 judge 是否可用。返回判对率；< 1.0 时应视为评测不可信。

    为什么必须有它：DeepEval 的忠实度指标在同一组用例上只判对 1/4（§1.1），
    而它看起来完全正常。**没有这个自检，你会拿一把坏尺子量很久。**
    """
    correct = 0
    for answer, ctx, expect_faithful in SELF_CHECK_CASES:
        result = await judge.faithfulness(answer, ctx)
        if (result["score"] == 1.0) == expect_faithful:
            correct += 1
        else:
            logger.error(
                "judge 自检失败：答案=%r 期望忠实=%s 实际=%s（理由：%s）",
                answer[:30], expect_faithful, result["score"] == 1.0, result["reason"][:60],
            )
    return correct / len(SELF_CHECK_CASES)
```

### 4.4 评测集（人工手标 20–30 条）

```yaml
# app/evals/qa_cases.yaml
# 人工标注。每条包含：
#   id / question / expected_doc_titles / key_points / tags / difficulty
# ★ expected_doc_titles 用于检索指标（不需要 LLM）
# ★ key_points 用于生成指标的完整性（需要 judge）—— 写成"必须覆盖的要点"
version: 1
cases:
  - id: refund_eta
    question: 退款需要多久到账？
    expected_doc_titles: ["售后政策"]
    key_points:
      - 客服 3 个工作日内完成审核
      - 审核通过后 5-7 个工作日退回原支付渠道
    tags: [退款, 时效]
    difficulty: easy

  - id: refund_eta_colloquial      # ★ 同义改写类：无关键词，考向量能力
    question: 钱什么时候退给我？
    expected_doc_titles: ["售后政策"]
    key_points:
      - 审核通过后 5-7 个工作日退回原支付渠道
    tags: [退款, 同义改写]
    difficulty: medium

  - id: return_exception           # ★ 例外条款类：容易答漏
    question: 哪些商品不能七天无理由退货？
    expected_doc_titles: ["售后政策"]
    key_points:
      - 定制类商品不支持
      - 生鲜类商品签收后 24 小时内可申请质量问题退货
    tags: [退货, 例外]
    difficulty: medium

  - id: cross_doc                  # ★ 跨文档类：考多文档召回
    question: 退款和发票这两件事分别有什么时间要求？
    expected_doc_titles: ["售后政策", "发票说明"]
    key_points:
      - 退款审核 3 个工作日、到账 5-7 个工作日
      - 发票需在下单后 7 天内申请
    tags: [跨文档]
    difficulty: hard

  - id: unanswerable               # ★ 不可回答类：考"拒答"能力（最容易幻觉的地方）
    question: 你们的 CEO 是谁？
    expected_doc_titles: []
    key_points: []
    expect_refusal: true           # ★ 期望明确回答"无法回答"，而不是编造
    tags: [拒答, 幻觉防线]
    difficulty: easy
```

**`expect_refusal` 这一类必须标注**：RAG 系统最危险的失败是**编造**。没有这类用例，你的评测会系统性低估幻觉率。

### 4.5 标注方法与建议分布

| 类别 | 建议条数 | 为什么要有 |
| --- | --- | --- |
| 直问（答案在单个切片里） | 8–10 | 基线，应该全对 |
| **同义改写**（无关键词重叠） | 4–6 | 考向量能力——**这是向量 vs 关键词的分水岭** |
| **跨文档**（需要多个文档） | 3–4 | 考验召回数量与融合 |
| **不可回答**（拒答） | 3–4 | 考幻觉防线 |
| **多轮追问**（依赖上下文） | 2–3 | 考查询改写（阶段 4） |
| 边界/例外条款 | 2–3 | 最容易答漏的一类 |

**总计 22–30 条。** 标注时记住：`expected_doc_titles` 要写**你希望被召回的文档**（不是"所有相关文档"），否则检索指标会失真。

## 5. 评测执行与回归

### 5.1 评测脚本（复用阶段 4 的 `eval_rerank.py` 骨架）

```bash
# 全量评测（检索指标零成本；生成指标每条约 0.0002 元）
.venv/bin/python scripts/eval_qa.py                    # 跑全部
.venv/bin/python scripts/eval_qa.py --tag 同义改写       # 只跑某类
.venv/bin/python scripts/eval_qa.py --no-judge          # 只跑检索指标（零成本）

# 对比两个配置（阶段 4 已用过这个模式）
RERANK_ENABLED=true  .venv/bin/python scripts/eval_qa.py --json out_rerank_on.json
RERANK_ENABLED=false .venv/bin/python scripts/eval_qa.py --json out_rerank_off.json
```

### 5.2 输出格式（要能进 CI）

```json
{
  "config": {"rerank_enabled": false, "embedding_enabled": true, "top_k": 5},
  "retrieval": {"hit@5": 0.95, "recall@5": 0.89, "mrr": 0.82},
  "generation": {"faithfulness": 0.92, "completeness": 0.78, "refusal_accuracy": 1.0},
  "cases": [{"id": "re", "passed": true, "details": {...}}],
  "cost_yuan": 0.0043,
  "judge_validated": true
}
```

**`judge_validated` 字段是刻意设计的**：它记录"本次评测的裁判通过了自检"。
**如果为 false，整份结果不应被采信**——这直接对应 §1 的教训。

### 5.3 基线（必须记录）

第一次跑出的数字就是**你的基线**。此后每次改动（改切分、改 top_k、改 prompt、开/关 rerank）都对着基线比。

**基线表（★ 已用真实 embedder + 真实 DeepSeek judge + 真实 PG 于 24 条用例实测填充）**：

| 配置 | hit@5 | mrr | faithfulness | completeness | 拒答准确率 | 成本 |
| --- | --- | --- | --- | --- | --- | --- |
| 纯关键词（阶段 3 行为，`--mode keyword --no-judge`） | 0.75 | 0.75 | — | — | — | 0（不用 judge） |
| 混合检索（当前，`--mode hybrid` 含 judge） | **1.0** | 0.95 | 1.0 | 0.925 | 1.0 | ≈0.052 元 / 24 条 |
| 混合 + rerank（`RERANK_ENABLED=true --no-judge`） | 1.0 | **0.975** | — | — | — | 0 |

> **这张表就是你简历上"召回率从 X 到 Y"的来源**：混合检索把 hit@5 从 **0.75 → 1.0**
> （4 条"同义改写"用例全靠向量救回，纯关键词全部 miss）。
>
> **★ rerank 那一行正是 §4.2 论点的实证**：开 rerank 后 hit@5 仍是 1.0（早已饱和、看不出差别），
> 而 **MRR 0.95 → 0.975**（把 `shipping_time` 的正确文档从 #2 提到 #1）——**这就是为什么需要 MRR 这把更精确的尺子**，
> 也是本阶段对阶段 4"只看 hit@k 得出 +0%"的方法论补强（呼应阶段 4 文档 §9.5 / §15.6）。基线原始 JSON 存档在 `app/evals/baseline_hybrid.json`。

### 5.4 CI 集成（可选但推荐）

```bash
# 快回归：只跑检索指标 + 少量 judge（零 LLM 成本或极低）
.venv/bin/python scripts/eval_qa.py --no-judge --fail-under-hit5 0.90

# 慢回归：发版前跑全量
.venv/bin/python scripts/eval_qa.py --fail-under-faithfulness 0.90
```

`--fail-under-*` 让脚本用**非零退出码**表示"低于基线"，这样 CI 能自动拦截效果退化。
**没有这个，改动导致的效果下降不会有人发现**——测试只保证"不崩"，不保证"不变差"。

## 9. 风险与取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **评测指标本身不可靠** | §1.1 实测 DeepEval 判对 1/4 | `validate_judge()` 自检；结果带 `judge_validated` 标记 |
| **裁判偏差**（self-preference） | 用自己的模型评自己，可能偏宽松 | 用已知坏答案校准；必要时换一个厂商的模型交叉验证 |
| 标注人力成本 | 20-30 条要人工写 | 这是**必要投入**——合成问题分布会偏离真实提问 |
| Langfuse 隐私 | 问题/切片/回答发往外部 | 默认 `LANGFUSE_ENABLED=false`；文档明确警示；敏感场景改自托管 |
| 评测成本 | 每条 judge 约 0.0002 元，30 条约 0.006 元 | 可忽略；且 `--no-judge` 模式零成本 |
| 评测与真实使用分布不一致 | 手标用例可能偏"规整" | 从 `chat_logs` 里挑**真实问过的问题**补进评测集 |

### 12.3 埋点为何不改变行为

### 12.4 真实评测过程（§9.5 式）

- 环境：真实 bge-small-zh-v1.5 embedder + bge-reranker-base + DeepSeek judge + 真实 PG（pgvector）。语料灌入独立评测用户 `__eval_qa__`，跑完级联删除，不污染真实数据。
- **绕开缓存/会话/限流**：直调 `retrieval.search` → `build_messages` → `llm.chat` → `judge`，但 prompt 与生成参数**复用 `qa.py` 同一实现**（评的才是线上真正跑的）。原因同阶段 4：答案缓存会让 rerank on/off 两趟返回同一缓存答案，A/B 对比失效。
- **先验证尺子**：跑正式评测前 `validate_judge()` 自检（4 个已知答案），不过则整份结果标 `judge_validated=false` 并非零退出。
- 结果见 §5.3 基线表。rerank 那行印证 §4.2：**MRR 比 hit@k 更能反映 rerank 的价值**。
