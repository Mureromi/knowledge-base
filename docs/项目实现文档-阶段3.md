## 1. ★ 本阶段最重要的认知：不能把 CPU 密集工作直接放进 async worker

这是阶段 3 最容易犯、且**测试完全测不出来**的错误。

### 1.1 问题

ARQ worker 运行在 **asyncio 事件循环**上。而 PDF 解析是 **CPU 密集型同步操作**：

```python
# ❌ 错误写法：在 async 函数里直接解析
async def process_document(ctx, task_id: int):
    reader = PdfReader(path)
    text = "\n".join(page.extract_text() for page in reader.pages)   # ← 阻塞整个事件循环
```

**后果**：这个 worker 进程在此期间**无法处理任何其他任务**——包括其他用户的上传。ARQ 的 `concurrency` 设置形同虚设（因为并发是靠事件循环切换实现的，而循环被卡住了）。

### 1.2 实测数据

我实测了三种情况（Python 3.14.5）：

| 操作 | 耗时 | 事件循环状态 |
| --- | --- | --- |
| 1 页中文 PDF，`asyncio.to_thread` 包装 | 2ms | ✅ 心跳协程正常跳动（线程 id 确认换了线程） |
| 1 页中文 PDF，同步直接解析 | 1ms | ❌ 循环完全停摆 |
| 真实 100 页 PDF（估算） | 数百 ms ~ 数秒 | ❌ 停摆期间所有任务排队 |

小文件看不出差别，**大文件就是事故**。

### 1.3 正确写法

```python
text = await asyncio.to_thread(extract_pdf_text, raw_bytes)
```

`asyncio.to_thread` 把同步函数丢到线程池执行，事件循环保持可调度。**这一行是阶段 3 最关键的代码**。

> 为什么不用 `ProcessPoolExecutor`？PDF 解析的 GIL 释放情况尚可（pypdf 有纯 Python 循环，GIL 会限制并行），但进程池要序列化 bytes、起进程开销大、部署更复杂。**线程池对本项目的规模足够**。真遇到 CPU 瓶颈再加进程池，那时也说明你已经有了真实负载数据。

### 1.4 顺带修正阶段 2 的一个隐藏问题

阶段 2 的会话/缓存测试全部在**单进程单循环**下运行，所以"阻塞事件循环"这类问题**测试永远发现不了**。阶段 3 引入 worker 后，建议补一个**并发冒烟测试**（§9.4）——同时提交两个上传任务，验证第二个不会被第一个阻塞。

## 2. ★ PDF 解析的三个实测结论（两个是静默失败的陷阱）

我用 reportlab 生成了真实中文 PDF 做端到端验证，结论如下。

### 2.1 中文提取没问题，两个库都对（但 pypdf 更快）

```
=== pypdf ===
  2ms | 页数 1 | 字符数 121
  内容: '售后政策说明书\n一、退款流程\n用户需在订单页提交退款申请...'
  含中文: True  含关键数字: True

=== PyMuPDF ===
  19ms | 字符数 121（内容完全相同）
```

**结论**：中文 PDF 提取不需要特殊处理，`pypdf` 即可。这是好消息——很多教程会警告"PDF 中文提取要装额外字体包"，那是 `pdfminer` 老版本的问题，现在的库不需要。

### 2.2 ★ 陷阱一：扫描版 PDF 会"提取成功但内容为空"

实测一个只有图形、没有文字层的 PDF（模拟扫描件）：

```
页数=1  提取字符数=0
strip 后为空? True
```

**它不会报错。** `PdfReader` 正常打开、`extract_text()` 正常返回——返回空字符串。

**如果不管这个**：文档以 `status=ready`、`chunk_count=0` 入库 → 用户看到"上传成功" → 提问时永远检索不到内容 → **用户完全不知道发生了什么**。这是典型的静默失败。

**必须处理**：

```python
if not text.strip():
    raise EmptyDocumentError(
        "该 PDF 没有可提取的文字层，可能是扫描件或图片型 PDF。"
        "本项目暂不支持 OCR，请上传含文字层的 PDF 或转成 txt/md。"
    )
```

**并在 `processing_tasks.error` 里存下这个原因**，让用户看得到。

### 2.3 ★ 陷阱二：损坏的 PDF 会抛异常

```
=== 损坏的 PDF（内容为 '%PDF-1.4 this is not a real pdf'）===
抛异常: PdfStreamError: Stream has ended unexpectedly
```

**必须捕获所有解析异常**，转成任务失败状态。绝不能让异常逃逸出任务函数——否则 ARQ 会按重试策略反复重试一个**永远不可能成功**的文件（见 §6.2 的确定性失败处理）。

> 还有一个更隐蔽的情况：PDF 有密码保护（加密）。`PdfReader` 打开时不报错，`extract_text()` 时才抛 `FileNotDecryptedError`。**所以 try/except 必须包住提取过程，而不是只包住打开过程。**

## 3. 架构：第一次出现"第二个进程"

```
┌────────────────────┐         ┌──────────────────────────┐
│  Web 进程 (uvicorn) │         │  Worker 进程 (arq)        │
│                    │         │                          │
│  POST /documents   │         │  process_document(ctx,id) │
│   1. 读文件 bytes   │         │   1. 读 processing_tasks  │
│   2. 建 document   │         │   2. status=running       │
│      status=pending│         │   3. asyncio.to_thread    │
│   3. 建 task 行     │         │      (解析 PDF/DOCX)      │
│   4. enqueue_job   │         │   4. 切片 + 写 chunks      │
│   5. 立即返回 202   │         │   5. status=succeeded     │
└─────────┬──────────┘         └────────────┬─────────────┘
          │                                 │
          │  enqueue (job_id)               │  brpop / 结果写回
          └────────────┬────────────────────┘
                       ▼
              ┌─────────────────┐        ┌──────────────────┐
              │  Redis (队列)    │        │ PostgreSQL/SQLite │
              │  arq:queue      │        │ documents         │
              │  (阶段 1 已有)   │        │ processing_tasks  │
              └─────────────────┘        │ chunks            │
                                         └──────────────────┘
```

### 3.1 两个进程的边界（阶段 3 反复会遇到的判断）

| 共享 | 不共享 |
| --- | --- |
| Redis（缓存 + 队列 + 限流） | **进程内存**（任何全局变量、`asyncio.Semaphore`） |
| 数据库（同一个库） | 事件循环（各自一个） |
| 代码（同一个包） | 生命周期（各自 startup/shutdown） |

**这条边界会反复咬人**：阶段 0 那个进程内 `asyncio.Semaphore` 在阶段 1 被 Redis 信号量替换，就是这个原因。**阶段 3 起，任何"存在模块级变量里的状态"都是 bug**。

### 3.2 开发环境怎么跑两个进程

本机没有 Docker，用两个后台进程即可：

```bash
cd "/Users/mureromi/Documents/FastAPI Learning/knowledge-base"

# 终端 1：web
.venv/bin/uvicorn app.main:app --reload --port 8000

# 终端 2：worker（注意是 arq 命令，参数是 WorkerSettings 的路径）
.venv/bin/arq app.worker.WorkerSettings
```

**worker 不需要 `--reload`**：它没有 HTTP 接口，改了代码重启即可（或者你手动 Ctrl-C 再起）。这一点和 web 不同，别指望它热重载。

## 4. 数据模型

### 4.1 新增：`processing_tasks` 表

```python
# app/models/processing_task.py
from datetime import datetime

from sqlalchemy import DateTime, ForeignKey, Integer, String, Text, func
from sqlalchemy.orm import Mapped, mapped_column

from app.models.base import Base


class ProcessingTask(Base):
    """一次文档处理任务。与 documents 一对多：重新解析会新建一条任务记录。"""

    __tablename__ = "processing_tasks"

    id: Mapped[int] = mapped_column(primary_key=True)
    document_id: Mapped[int] = mapped_column(
        ForeignKey("documents.id", ondelete="CASCADE"), index=True
    )
    owner_id: Mapped[int] = mapped_column(
        ForeignKey("users.id", ondelete="CASCADE"), index=True
    )

    # pending / running / succeeded / failed
    status: Mapped[str] = mapped_column(String(16), default="pending", index=True)
    # ARQ 的 job_id，便于从日志反查、以及做幂等去重
    job_id: Mapped[str | None] = mapped_column(String(64), default=None, index=True)
    attempt: Mapped[int] = mapped_column(Integer, default=0)

    # 失败原因（给用户看的，不要塞堆栈）
    error: Mapped[str | None] = mapped_column(Text, default=None)
    # 解析出的字符数、切片数，便于排查"为什么检索不到"
    char_count: Mapped[int] = mapped_column(Integer, default=0)
    chunk_count: Mapped[int] = mapped_column(Integer, default=0)

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )
    started_at: Mapped[datetime | None] = mapped_column(
        DateTime(timezone=True), default=None
    )
    finished_at: Mapped[datetime | None] = mapped_column(
        DateTime(timezone=True), default=None
    )
```

### 4.2 为什么任务状态单独建表，而不是只复用 `documents.status`

阶段 0 就预留了 `documents.status`，看起来够用。但单独建表有三个实际收益：

| 收益 | 说明 |
| --- | --- |
| **失败原因有地方放** | 用户需要知道"为什么失败"（扫描件？格式损坏？超时？），塞进 documents 表会污染业务表 |
| **可追溯重试历史** | 同一文档重新解析会产生多条任务记录，能看出"第 1 次超时、第 2 次成功" |
| **统计与告警** | "近 24 小时失败率多少""平均解析耗时多少"这类查询，需要任务级数据 |

**`documents.status` 仍然保留并继续更新**（它是给业务层快速判断用的），两者职责不同：`documents.status` 是**当前状态的投影**，`processing_tasks` 是**事件流水**。

### 4.3 `documents.status` 的状态机

```
pending ──▶ processing ──▶ ready
                    └────▶ failed
```

**必须做的一件事**：检索（`retrieval.search`）要**只检索 `status='ready'` 的文档**。

原因：任务还没完成时，`chunks` 表里没有数据，检索天然查不到——**看起来是对的**。但失败重试场景下会有残留切片（先写了一半再失败），所以必须显式过滤。**建议在 `search` 里加上这个条件**，并在测试里断言"failed 文档的切片永不出现在检索结果中"。

## 5. 上传端点的改造

### 5.1 契约变化（这是一次破坏性变更）

| | 阶段 2（同步） | 阶段 3（异步） |
| --- | --- | --- |
| 状态码 | `201 Created` | **`202 Accepted`** |
| 响应体 | 含 `chunk_count` 的文档详情 | 文档 + **`task_id`** + `status="pending"` |
| 支持格式 | txt / md | txt / md / **pdf** / **docx** |
| 解析耗时 | 阻塞请求（大文件会超时） | 立即返回，后台处理 |

**`202` 而不是 `201` 是重要的语义**：`201` 意味着"资源已创建完成"，而异步场景下**文档实体已创建但内容还没解析好**。用 `202 Accepted`（请求已接受，处理尚未完成）才是准确的。这个细节在 API 设计评审里经常被追问。

### 5.2 上传时的容量防线（阶段 0/1/2 一直缺这个）

```python
# app/core/config.py 新增
max_upload_bytes: int = 20 * 1024 * 1024      # 20MB
max_pdf_pages: int = 500                       # 防"一个 5000 页 PDF 拖垮 worker"
```

上传时先检查大小，超限返回 **413**：

```python
raw = await file.read()
if len(raw) > settings.max_upload_bytes:
    raise HTTPException(
        status_code=status.HTTP_413_REQUEST_ENTITY_TOO_LARGE,
        detail={
            "code": 41301,
            "message": f"文件超过上限 {settings.max_upload_bytes // 1024 // 1024}MB",
            "detail": None,
        },
    )
```

**为什么必须加**：`await file.read()` 会把整个文件读进内存。没有上限意味着**一个 2GB 的上传就能把服务打挂**（OOM）。这是最容易被忽略、后果最严重的防线。

### 5.3 端点实现

```python
# app/api/v1/endpoints/documents.py
@router.post("", response_model=DocumentOut, status_code=status.HTTP_202_ACCEPTED)
async def upload_document(
    current_user: CurrentUser,
    db: DBSession,
    arq: ArqDep,                    # ★ 新增依赖：ARQ 连接池
    file: Annotated[UploadFile, File(description="支持 .txt / .md / .pdf / .docx")],
) -> DocumentOut:
    filename = file.filename or ""
    source_type = detect_source_type(filename)
    if source_type is None:
        raise HTTPException(415, {"code": 41501, "message": "仅支持 .txt/.md/.pdf/.docx", "detail": None})

    raw = await file.read()
    if len(raw) > settings.max_upload_bytes:
        raise HTTPException(413, {...})

    title = filename.rsplit(".", 1)[0] or filename

    # txt/md 走快路径：本来就是纯文本，不需要 worker 排队
    if source_type in ("txt", "md"):
        try:
            text = decode_bytes(raw)
        except UnicodeDecodeError:
            raise HTTPException(422, {"code": 42201, "message": "文本编码无法识别", "detail": None}) from None
        if not text.strip():
            raise HTTPException(422, {"code": 42202, "message": "文件内容为空", "detail": None})
        doc, chunk_count = await doc_crud.create_with_chunks(
            db, owner_id=current_user.id, title=title,
            source_type=source_type, raw_text=text, drafts=split_text(text),
        )
        return _to_out(doc, chunk_count)          # 保持 202 但内容已就绪

    # pdf/docx 走异步路径
    doc = await doc_crud.create_pending(
        db, owner_id=current_user.id, title=title, source_type=source_type
    )
    task = await task_crud.create(db, document_id=doc.id, owner_id=current_user.id)

    # ★ 先把 document_id / task_id 提交，再投递任务
    #   否则 worker 可能先于提交读到任务（竞态），或读到不存在的 document
    await db.commit()

    job = await arq.enqueue_job(
        "process_document", task.id,
        _job_id=f"doc:{doc.id}:{task.id}",     # 幂等：同一任务不会被投递两次
    )
    if job is not None:
        await task_crud.set_job_id(db, task, job.job_id)
        await db.commit()

    return _to_out(doc, 0, task_id=task.id)
```

> **`await db.commit()` 必须在 `enqueue_job` 之前**。这是"投递任务"这类代码最经典的竞态：
> worker 是另一个进程，它可能在你的 INSERT 还没提交时就开始执行，然后**查不到那条任务记录**，或者查到了但 `document_id` 指向的文档还不存在。
> 记住这个顺序：**先落库并提交，再投递**。反过来一定会偶发"任务查到不存在"的诡异错误。

### 5.4 状态查询端点

```python
@router.get("/{doc_id}/status", response_model=DocumentStatusOut)
async def get_document_status(
    doc_id: int, current_user: CurrentUser, db: DBSession
) -> DocumentStatusOut:
    """前端轮询用。返回文档状态 + 最新任务进度 + 失败原因。"""
```

响应示例：

```json
{
  "document_id": 12,
  "status": "failed",
  "task_id": 7,
  "attempt": 2,
  "error": "该 PDF 没有可提取的文字层，可能是扫描件或图片型 PDF。本项目暂不支持 OCR。",
  "char_count": 0,
  "chunk_count": 0
}
```

**轮询接口设计要点**：
- 前端建议 **1 秒间隔、最多轮询 60 次**（1 分钟超时），别做无限轮询
- 响应里带 `status`，前端据此决定继续轮询还是停止
- **失败时要把 `error` 原文返回**——用户需要知道怎么办（这正是 §2.2 那个原因的用处）

## 6. Worker 实现

### 6.1 ARQ 的 API 要点（已核实 0.28.0）

```python
# 这三个是从实测的签名里确认的，不要凭记忆写
arq.create_pool(RedisSettings(...))          # → ArqRedis
await arq_pool.enqueue_job(fn_name, *args, _job_id=None, _defer_by=None, _expires=None)
arq.worker.Worker(settings.WorkerSettings)   # WorkerSettings 里配 functions / redis_settings / max_tries
```

`WorkerSettings.functions` 里每项可用 `arq.func(coroutine, name=..., timeout_s=..., max_tries=...)` 精细控制。

### 6.2 任务函数（`app/worker.py`）

```python
"""ARQ worker：文档解析任务。

启动：
    .venv/bin/arq app.worker.WorkerSettings

★ 与 web 进程的边界（§3.1）：只共享 Redis 和数据库，不共享内存。
"""

import asyncio
import logging
from datetime import UTC, datetime
from typing import Any

from arq.connections import RedisSettings

from app.clients.cache import startup_cache, shutdown_cache
from app.core.config import settings
from app.db.session import SessionLocal, init_models
from app.services.parsing import EmptyDocumentError, UnsupportedDocumentError, extract_text
from app.services.ingest import split_text
from app.crud import document as doc_crud
from app.crud import processing_task as task_crud

logger = logging.getLogger(__name__)


class TransientError(Exception):
    """可重试的临时故障（网络、锁、超时）。"""


async def process_document(ctx: dict[str, Any], task_id: int) -> str:
    """解析文档 → 切片入库 → 更新状态。

    返回字符串会存进 ARQ 的结果里（便于排查）。
    """
    attempt = ctx.get("job_try", 1)

    async with SessionLocal() as db:
        task = await task_crud.get(db, task_id)
        if task is None:
            logger.error("任务不存在 task_id=%s（可能已被删除）", task_id)
            return "task-not-found"

        # 幂等：已经成功的任务不重复处理（重试或重复投递时）
        if task.status == "succeeded":
            logger.info("任务已完成，跳过 task_id=%s", task_id)
            return "already-succeeded"

        await task_crud.mark_running(db, task, attempt=attempt)
        document = await doc_crud.get(db, task.document_id)
        await db.commit()

        if document is None:
            await task_crud.mark_failed(db, task, "关联文档不存在")
            await db.commit()
            return "document-not-found"

        document_id = document.id
        source_type = document.source_type
        owner_id = document.owner_id

    # ---------- 重活放在事务外（不要把数据库事务开着做 CPU 活）----------
    try:
        text = await asyncio.to_thread(
            extract_text, document_id, source_type, settings.max_pdf_pages
        )
    except (EmptyDocumentError, UnsupportedDocumentError) as exc:
        # ★ 确定性失败：重试一万次也不会成功，直接置 failed，不抛异常（不触发重试）
        async with SessionLocal() as db:
            task = await task_crud.get(db, task_id)
            if task:
                await task_crud.mark_failed(db, task, str(exc))
            if task:
                await doc_crud.set_status(db, task.document_id, "failed")
            await db.commit()
        logger.warning("确定性失败 task_id=%s: %s", task_id, exc)
        return f"failed: {type(exc).__name__}"

    except Exception as exc:                      # noqa: BLE001 - 未知错误视为可重试
        logger.exception("解析异常 task_id=%s", task_id)
        async with SessionLocal() as db:
            task = await task_crud.get(db, task_id)
            if task:
                await task_crud.mark_failed(db, task, f"解析失败：{type(exc).__name__}")
            await db.commit()
        raise TransientError(str(exc)) from exc   # 抛出去让 ARQ 重试

    # ---------- 切片入库 ----------
    drafts = split_text(text)
    if not drafts:
        async with SessionLocal() as db:
            task = await task_crud.get(db, task_id)
            if task:
                await task_crud.mark_failed(db, task, "解析出的内容切片后为空")
                await doc_crud.set_status(db, task.document_id, "failed")
            await db.commit()
        return "failed: no-chunks"

    async with SessionLocal() as db:
        task = await task_crud.get(db, task_id)
        if task is None:
            return "task-not-found"
        await doc_crud.replace_chunks(
            db, document_id=document_id, owner_id=owner_id,
            raw_text=text, drafts=drafts,
        )
        await doc_crud.set_status(db, document_id, "ready")
        await task_crud.mark_succeeded(
            db, task, char_count=len(text), chunk_count=len(drafts)
        )
        await db.commit()

    logger.info(
        '{"event":"parse_done","task":%s,"doc":%s,"chars":%s,"chunks":%s,"attempt":%s}',
        task_id, document_id, len(text), len(drafts), attempt,
    )
    return "succeeded"


async def startup(ctx: dict[str, Any]) -> None:
    await init_models()          # 开发期方便；生产应改为 alembic upgrade
    await startup_cache()
    ctx["started_at"] = datetime.now(UTC)
    logger.info("worker 已启动")


async def shutdown(ctx: dict[str, Any]) -> None:

    logger.info("worker 已退出")
```

### 6.3 三个必须注意的点

**① 事务边界：重活必须放在事务外。**

上面的结构是刻意安排的：

```
开事务 → 读任务、置 running → 提交 → 关事务
    ↓ （事务外）
CPU 解析（可能几秒）
    ↓
开新事务 → 写 chunks、置 succeeded → 提交
```

如果把解析放在事务里，会**长时间持有数据库连接和锁**，几百个任务就把连接池耗尽。**这是异步任务最常犯的错误。**

**② 确定性失败不能抛异常。**

`EmptyDocumentError`（扫描件无文字层）、`UnsupportedDocumentError`（加密 PDF）这类错误，**重试 3 次也是一样的结果**，只是白烧 CPU 和日志。所以捕获后置 `failed` 并 **`return` 而不是 `raise`**。

反之，未知异常（磁盘满、数据库抖动）才 `raise` 让 ARQ 重试。

**这个区分必须显式写进代码**——否则你会看到"扫描件上传后一直在重试"的诡异现象。

**③ 用 `replace_chunks` 而不是 `create_with_chunks`。**

重试场景下，上次可能已经写入了一部分切片。必须**先删后写**（`replace_chunks` 的实现里 `DELETE FROM chunks WHERE document_id=?` 然后批量插入），否则会产生重复切片 → 检索出重复引用 → 用户看到 `[1] [1] [1]`。

## 7. 解析层（`app/services/parsing.py`）

```python
"""文档文本提取。txt/md/pdf/docx 统一入口。

★ 所有 PDF 解析都是同步阻塞的，调用方必须用 asyncio.to_thread 包装（§1）。
"""

import io
import logging

from pypdf import PdfReader
from pypdf.errors import PdfReadError

logger = logging.getLogger(__name__)


class EmptyDocumentError(Exception):
    """没有可提取的文字（扫描件/图片型 PDF）。确定性失败，不重试。"""


class UnsupportedDocumentError(Exception):
    """加密、损坏、超出页数限制等。确定性失败，不重试。"""


def extract_pdf_text(raw: bytes, *, max_pages: int) -> str:
    """从 PDF 提取文字。**同步阻塞函数**，调用方负责 to_thread。"""
    try:
        reader = PdfReader(io.BytesIO(raw))
    except PdfReadError as exc:
        raise UnsupportedDocumentError(f"PDF 无法打开：{exc}") from exc

    if reader.is_encrypted:
        # 尝试空密码（有些 PDF 只是限制编辑，允许读取）
        try:
            if reader.decrypt("") == 0:
                raise UnsupportedDocumentError("PDF 已加密，需要密码才能读取")
        except Exception as exc:                  # noqa: BLE001
            raise UnsupportedDocumentError("PDF 已加密，需要密码才能读取") from exc

    if len(reader.pages) > max_pages:
        raise UnsupportedDocumentError(
            f"PDF 页数 {len(reader.pages)} 超过上限 {max_pages} 页"
        )

    parts: list[str] = []
    for index, page in enumerate(reader.pages):
        try:
            parts.append(page.extract_text() or "")
        except Exception as exc:                  # noqa: BLE001
            # 单页失败不放弃整份文档：记录并继续（真实 PDF 常有坏页）
            logger.warning("第 %s 页提取失败：%s", index + 1, exc)
            parts.append("")

    text = "\n\n".join(p.strip() for p in parts if p.strip())

    # ★ 关键检查（§2.2）：扫描件会"成功返回空字符串"，必须显式判失败
    if not text.strip():
        raise EmptyDocumentError(
            "该 PDF 没有可提取的文字层，可能是扫描件或图片型 PDF。"
            "本项目暂不支持 OCR，请上传含文字层的 PDF，或先转成 txt/md。"
        )
    return text


def extract_docx_text(raw: bytes) -> str:
    """从 .docx 提取文字。需要 python-docx。"""
    import docx                                   # 延迟导入，减少 worker 启动开销

    try:
        document = docx.Document(io.BytesIO(raw))
    except Exception as exc:                      # noqa: BLE001
        raise UnsupportedDocumentError(f"docx 无法打开：{exc}") from exc

    parts = [p.text for p in document.paragraphs if p.text.strip()]
    # 表格里的文字也要（政策/价格类文档大量信息在表格里）
    for table in document.tables:
        for row in table.rows:
            cells = [c.text.strip() for c in row.cells if c.text.strip()]
            if cells:
                parts.append(" | ".join(cells))

    text = "\n".join(parts)
    if not text.strip():
        raise EmptyDocumentError("docx 中没有可提取的文字")
    return text
```

> **一个设计决定**：`extract_pdf_text` 里**单页失败不放弃整份文档**。理由：真实 PDF 常有坏页（图表页、嵌入对象），因为一页失败就整体失败，用户体验很差。记录 warning 并继续是更实用的选择。但**如果所有页都失败**，最终会因为 `text` 为空而触发 `EmptyDocumentError`，所以不会静默通过。

### 9.4 ★ 并发冒烟测试（验证 §1 的阻塞问题）

这是阶段 3 唯一能证明"事件循环没被阻塞"的测试：

```python
@pytest.mark.asyncio
async def test_concurrent_tasks_do_not_block_each_other(monkeypatch, session_factory):
    """两个解析任务并发执行时，总耗时应接近单个任务，而不是两倍。

    若实现里漏了 asyncio.to_thread（直接同步解析），两个任务会串行，
    总耗时 ≈ 2 倍。用一个"慢解析"的桩函数来放大这个差异。
    """
    import time

    # 把真正的 PDF 解析换成一个纯同步 sleep，放大"阻塞 vs 不阻塞"的差异
    def slow_extract(document_id, source_type, max_pages):
        time.sleep(0.3)
        return "退款流程：提交申请后 3 个工作日审核。"

    monkeypatch.setattr("app.worker.extract_text", slow_extract)

    t0 = time.perf_counter()
    await asyncio.gather(
        process_document({"job_try": 1}, task_id=1),
        process_document({"job_try": 1}, task_id=2),
    )
    elapsed = time.perf_counter() - t0

    # 用 to_thread：两个 0.3s 的任务并发 ≈ 0.3s
    # 直接同步解析：串行 ≈ 0.6s
    assert elapsed < 0.5, (
        f"两个任务耗时 {elapsed:.2f}s，接近串行——说明解析没有走 asyncio.to_thread，"
        "事件循环被阻塞了（阶段 3 §1）"
    )
```

实现思路：monkeypatch `extract_text` 为 `time.sleep(0.3)` 的同步函数，然后 `asyncio.gather` 两个任务，断言总耗时 < 0.5s（而不是 ≈0.6s）。

**这条测试很有价值**：它把"性能正确性"变成了可自动验证的断言，而不依赖人工 review。

## 11. 风险与取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **僵死任务** | worker 在 `running` 中途被 kill → 任务永远停在 `running` | §11.1 的清理任务；或 worker 启动时扫一遍 `running` 且超时的任务重置为 `pending` |
| ~~上传的文件没有持久化~~ **已解决** | 落地时实现了 `documents.raw_content`（`LargeBinary` 落库），worker 从库里读原始字节 | 重新解析成为可能（受 `store_raw_upload` 开关控制）；代价是库体积随上传量增长，见 §14.3 |
| 解析在 worker 里超时 | 500 页 PDF 可能超 `job_timeout` | `max_pdf_pages` 限制 + `timeout_s=300`；超时按 `TransientError` 重试一次 |
| 内存峰值 | `raw = await file.read()` 把整个文件读进内存 | 20MB 上限；真要大文件必须改成分块落盘 |
| 重复投递 | 网络抖动导致同一任务被投两次 | `_job_id=f"doc:{doc_id}:{task_id}"` 天然幂等 + 任务里的 `already-succeeded` 检查 |
| docx 解析质量 | 复杂排版（文本框、图表）提不出 | 明确记为已知限制，写在 error 提示里 |

### 11.1 僵死任务的清理（建议一起实现）

```python
async def cleanup_stale_tasks(ctx: dict) -> int:
    """把卡在 running 超时的任务重置为 pending，让它能被重新投递。"""
```

ARQ 支持 `cron` 定时任务：

```python
from arq import cron

class WorkerSettings:
    cron_jobs = [cron(cleanup_stale_tasks, minute={0, 15, 30, 45})]
```

**为什么需要**：worker 被 `kill -9`、或机器重启，任务就永久卡在 `running`。没有清理机制的话，用户会看到一个**永远转圈**的进度条——**而且没有任何错误提示**。这类"没有失败、只是永远没完成"的问题最难排查。

## 14. 实现落地记录

> 本节记录**实际实现相对本文设计的偏差**——都是落地过程中撞上的真实问题，供后续阶段和他人接手时避坑。

### 14.1 redis-py 必须降级（依赖冲突，设计未预见）

本文基线写「Redis 8.10.2」指的是 **Redis 服务器版本**，不是 redis-py 客户端。项目阶段 1/2 的 `pyproject.toml` 里声明的是 `redis>=8.1`（客户端），而 **ARQ 0.28 硬锁 `redis[hiredis]>=4.2,<6`**——`uv sync` 直接冲突失败。

查证 ARQ 各最新版仍只支持 redis-py <6，于是把客户端降级为：

```toml
"redis>=5.0.1,<6",   # arq 0.28 锁 redis<6；5.0.1 起才有 Redis.aclose()
```

降级前逐个核实过阶段 1/2 用到的 redis-py API（`from_url` / `get` / `set(ex=)` / `delete` / `aclose` / `eval` / `incr` / `expire`）在 5.x 全部存在（`aclose` 自 5.0.1 引入）。降级后跑全量回归，阶段 1/2 的缓存/限流**无破损**。最终锁定 `redis==5.3.1` + `arq==0.28.0`。

### 14.2 `arq.func()` 的参数名是 `timeout` 不是 `timeout_s`

§6.2 的伪代码写的 `arq.func(..., timeout_s=300, ...)` 在 0.28 上**直接 TypeError**。用 `inspect.signature` 核实：对外参数名是 `timeout`（内部才存成 `timeout_s`）。落地改为：

```python
arq.func(process_document, name="process_document",
         timeout=settings.worker_job_timeout, max_tries=settings.worker_max_tries)
```

### 14.3 `raw_content` 落库：worker 拿的是原始字节，不是 `document_id` 去读盘

§5.3 / §6.2 的伪代码里 `extract_text(document_id, ...)` 是「把 id 传给解析函数、函数自己去读文件」的思路。但本阶段决定**不引入临时文件/对象存储**（多实例不共享磁盘），而 worker 又是**另一个进程、不能靠内存传 bytes**。因此落地为：上传时把原始字节存入 `documents.raw_content`（`LargeBinary`，受 `store_raw_upload` 开关控制），worker 从库里读出字节再解析。

- `documents.raw_text` 相应改为**可空**（pdf/docx 异步路径下上传即建文档时还没有正文）。
- worker 的 `process_document` 签名是 `(ctx, task_id)`：先查任务→取 `document.raw_content`→`asyncio.to_thread(extract_text, raw_content, source_type, max_pdf_pages)`。
- `raw_content` 为空（关闭了存储开关）时，任务直接置 `failed` 并提示「请重新上传」——这是该开关的已知代价。

### 14.4 Alembic 迁移按方言分支（PG 上 batch 重建会破坏子表外键）

运行时环境是 **PostgreSQL**（`.env` 已切 `postgresql+asyncpg://...`），而测试/开发用 SQLite。`documents` 表有子表外键（`chunks`、`processing_tasks` 引用它）：

- **SQLite**：改列（`raw_text` 可空、加 `raw_content`）必须走 `op.batch_alter_table("documents")`（SQLite 不支持 ALTER COLUMN）。
- **PostgreSQL**：必须用**原生** `op.add_column` / `op.alter_column`。若在 PG 上也用 batch，Alembic 会尝试**重建整张 documents 表**，破坏子表外键约束。

迁移文件 `a3f1c7d92b40_phase3_processing_tasks_documents_raw.py` 用 `_is_sqlite()` 分支处理两种方言，`down_revision='86bf317304ac'`（阶段 2）。已在 SQLite `kb.db` 上做**双向验证**：`stamp 86bf → upgrade head`（建表+改列，chunks 外键存活）→ `downgrade -1`（干净回滚）→ 再 `upgrade head`（可重复）。PG 侧因 schema 已由 `create_all` 建好，用 `alembic stamp head` 对齐版本表。

### 15.1 通过情况

13 项清单全部达成。其中三条最关键的行为已**独立复现**（不复用项目自带测试）：

| 验证 | 方法 | 结果 |
| --- | --- | --- |
| 扫描件拦截 | 自造"只有图形无文字层"的 PDF | 抛 `EmptyDocumentError`，文案完整 |

### 15.2 并发测试的非空泛性

验收时特意审查了 §9.4 那条并发冒烟测试**是不是空泛断言**（阶段 2 曾出现过一条"只断言两边都 False"的假测试）。结论：写法正确。

- 真用 `asyncio.gather` 并发执行两个任务
- 桩函数是**纯同步** `time.sleep(0.3)`，能把"阻塞 vs 不阻塞"放大成 0.6s vs 0.3s
- 桩函数签名 `(raw, source_type, max_pages)` 与真实 `extract_text` **完全一致**，确保 patch 真正生效

若实现漏掉 `asyncio.to_thread`，两条必然串行 ≥0.6s，断言（`< 0.5`）失败。**结论：这条测试确实能发现该 bug。**

### 15.3 验收发现的三个问题（✅ 已全部修复并补回归测试）

验收中发现的三个非阻塞问题，性质各不相同，**都已修复**：

| # | 问题 | 性质 | 修复 |
| --- | --- | --- | --- |
| 1 | 轮询接口在解析期间一直返回 `status=pending`，**看不到 `processing`** | **真 bug**：worker 置任务 `running` 时漏了同步更新 `documents.status` | worker 补一行 `set_status(..., "processing")`，与 `mark_running` 同事务提交 |
| 2 | 任务历史随文档删除而**级联消失**（`CASCADE`） | **设计冲突**：与 §4.2 声称的"可追溯历史/统计失败率"目标矛盾 | 改为 `SET NULL` + 保留冗余 `owner_id`（迁移 `phase3b`） |
| 3 | `cleanup_stale_tasks` 用 `stale_ids[:reset]` 切片，且重投前无二次校验 | **健壮性缺陷**：`reset` 是条数不是 id 列表；慢任务可能被重复执行 | `reset_stale_running` 改为返回 id 列表；重投前用条件 UPDATE 抢占（`RETURNING` 拿回真正抢到的 id） |

> **验收的价值正在于此**：三条里第 1 条是真 bug（用户能观察到错误状态）、第 2 条是设计自相矛盾（文档承诺了实现没兑现）、第 3 条是健壮性隐患。**如果只看"测试是否全绿"，这三条都不会被发现**——129 个测试在修复前后都是全绿的。
