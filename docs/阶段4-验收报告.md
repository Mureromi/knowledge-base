## 二、独立验证明细（我实际跑的，不复用项目自带测试）

### 2.1 回填与向量列

```
总切片 4，已向量化 4，完成度 100.0%
vector_dims(embedding) = 512        ← 与 bge-small-zh-v1.5 一致
```

### 2.2 ★ worker 侧向量写入（清单第 5 项，最容易"接线了但没生效"的一项）

上传一个真实中文 PDF，走 **真实 uvicorn + 真实 arq worker + 真实 PostgreSQL**：

```
上传 HTTP 202, doc_id=25, status=pending
轮询 → status=ready, chunk_count=1
查库 → chunks.id=24, has_vec=t, vector_dims=512    ← ✅ worker 确实写了向量
```

**为什么特意验这项**：阶段 3 验收时我发现过类似问题（`processing` 状态代码写了但没生效）。"代码接线了"和"真的生效了"是两件事——尤其这条路径跨了**两个进程**（web 投递 → worker 编码入库），中间任何一环断掉都不会报错。

### 2.3 同义改写检索（向量检索相对关键词的核心价值）

```
问: 钱什么时候退给我
答: 审核通过后，款项将在 5-7 个工作日退回原支付渠道[1]。
```

**"钱什么时候退给我"里没有"退款/到账/工作日"任何一个关键词**——纯关键词检索必然失败。这条是向量能力生效的直接证据。

### 2.4 多轮追问（阶段 2 遗留问题，由阶段 4 的改写解决）

```
第 1 轮: 退款要多久到账？      → 正确回答
追问  : 那退货呢？            → 正确命中退货内容
引用  : policy (score 4.44, keyword_rank=1, vector_rank=1)
        invoice (score -1.98, vector_rank=2)
```

两点值得记录：

1. **改写确实生效**：阶段 2 时「那退货呢？」这类追问的向量检索基本必然失败（单看这句无法定向量）。
2. **`keyword_rank` / `vector_rank` 字段很有用**：一眼看出 policy 是两路都命中（rank 1/1）、invoice 只被向量召回（rank null/2）。这是排查"为什么这条被排进来"的直接线索——**阶段 4 新增的这两个字段是排障利器**。

### 2.5 rerank 分数为负是正常的

上例里 invoice 的 `score = -1.98`。**负分不代表错误**，它是 cross-encoder 的 logit 经 sigmoid 后的值，只用于排序。
文档 §6.2 已明确警告"不能拿 rerank 分数设阈值"——**这一条在真实输出里得到印证**：若照抄"低于 0.3 丢弃"的写法，这个候选会被直接扔掉。

## 三、对关键实现的审查结论

### 3.1 ★ 三处"刻意偏离伪代码"都是**正确的改进**

文档 §15.2 记录了三处与伪代码的偏离，我逐条核对，**三处都是必要的**：

| # | 偏离 | 审查结论 |
| --- | --- | --- |
| 1 | rerank 加了 try/except | ✅ **必须加**。伪代码里 `reranker.rerank()` 抛错会冒泡成 500——为了一个可选优化把整次问答搞挂，是最典型的"优化引入故障" |
| 2 | 向量召回按方言分支（PG 用 `<#>`，其他走应用层余弦） | ✅ **巧妙**。既满足"生产用 pgvector 原生算子"，又让测试无需真实 PG 就能验证召回顺序 |
| 3 | 向量路包 try/except，异常时 `vector_pairs=[]` | ✅ **正确的降级方向**。关键词路仍能工作，服务不降级为不可用 |

**这三处的共同点**：都在"可选优化"外面包了保护层，确保**优化失败时退回到上一个可用状态**，而不是让服务挂掉。这是阶段 4 里最值得保留的设计习惯。

### 3.2 ★ 测试隔离的处理很到位

`conftest` 加了 autouse 夹具 `_isolate_query_rewrite`，**默认关掉查询改写**（§15.3）。理由说得很清楚：改写会多调一次 LLM、并把改写句喂给检索，这会让阶段 2/3 的会话与缓存测试（假定"一轮只调一次 LLM"）误红。

**这是正确的做法**：不是去改那些老测试的断言，而是让新功能在存量测试里**默认不生效**，再由 `test_query_rewrite.py` 显式打开逐例验证。如果反过来（默认开、再去改 133 个老测试），既费事又容易掩盖真实的回归。

### 3.3 ★ 渐进降级（`embed_documents_if_ready`）的设计

模型未就绪或编码失败时返回 `None` → 调用方不写 embedding → 切片仍可被关键词召回。

**这个设计有两个收益**：
1. **向量环节绝不阻断入库**（模型下载失败也不影响上传功能）
2. **测试环境不需要模型**（`is_ready=False` 时行为与阶段 3 完全一致，133 个存量测试无需改动）

**一个设计同时解决了"生产健壮性"和"测试可隔离性"**——这是阶段 4 里我最欣赏的一处。

### 3.4 rerank 增量评测的方法论很扎实（§15.6）

这项是"最容易被糊弄过去"的验收项（很容易写成"跑了脚本，效果不错"）。实际做法值得肯定：

| 做法 | 为什么重要 |
| --- | --- |
| 用**真实** embedder + reranker + 真实 PG | 假实现测不出真实的排序行为 |
| **绕开查询改写**直接调 `retrieval.search` | 隔离变量——否则分不清提升来自改写还是 rerank |
| 语料**刻意含关键词撞车近邻**（refund/return/shipping/privacy） | 简单语料上 rerank 必然"看起来没用"，撞车语料才暴露它的真实作用 |
| 只翻转 `rerank_enabled` 跑两趟 | 单变量对照 |
| 用独立评测用户、跑完级联删除 | 不污染真实数据 |
| **记录了"带偏 1 例"** | 诚实地报告负面影响，而不是只挑好的说 |

**结论也下得诚实**：+6% 落在文档预设的"0~10% → 保留但记录权衡"档，于是建议**默认关闭但保留代码**——理由是 Top-5 已 100% 饱和，rerank 的作用仅剩"在已召回候选里挪动 #1"，为此常驻 1GB 不划算。

> **这正是 §1.1 那个"架构正确 ≠ 立即有收益"的实证。** 从文档里"我实测发现 rerank 可能零提升"的预警，到真实评测得出"+6%、建议关闭"，形成了一条完整的证据链。**这是本项目里最接近工程决策的一次实践。**

## 四、★ 需要处理的一处不一致

**问题**：§15.6 的结论是"建议部署默认 `RERANK_ENABLED=false`"，但配置三处都是 `true`：

| 位置 | 当前值 |
| --- | --- |
| `app/core/config.py:125` | `rerank_enabled: bool = True` |
| `.env:57` | `RERANK_ENABLED=true` |
| `.env.example:89` | `RERANK_ENABLED=true` |

**而且 `config.py` 里的注释自己就写着"故默认可关"**——注释与代码矛盾：

```python
# Rerank（本地 bge-reranker-base，约 1GB 内存代价）
# ★ 可一键对比开关。§1.1 实测：小语料下 rerank 几乎没有提升，故默认可关。
rerank_enabled: bool = True          # ← 注释说"默认可关"，代码却是 True
```

**后果**：真跑起来会常驻一个约 1GB 的 cross-encoder（实测 web 进程 RSS 从 363MB 涨到 1164MB），
换来的是 Top-1 +6%、Top-5 +0%。**评测的价值没有转化到配置上。**

**两种处理方式**：

| 选项 | 理由 |
| --- | --- |
| **A. 改成 `false`（符合评测结论）** | 省 801MB；Top-5 不受影响（100% 饱和）；代码保留，语料长大后改一行即可复测 |
| B. 保持 `true`（接受内存代价） | 若你的文档集会持续增长，早晚要用；常开省得忘记打开 |

**这是产品决策，不是技术决策**，所以本报告不擅自改动，列为待确认项。**建议选 A**——理由是你现在只有 4 个文档、Top-5 已饱和，此时常开 1GB 模型的收益接近 0。

## 八、决策落实记录（2026-10-13）

§四指出的 `RERANK_ENABLED` 不一致**已按评测结论处理**：默认改为 `false`，三处配置一致。

### 8.1 实测收益

| 指标 | 开启 rerank | 关闭 rerank | 变化 |
| --- | --- | --- | --- |
| web 进程 RSS | 1164 MB | **335 MB** | **-829 MB（-71%）** |
| 启动耗时 | ≈120s（首次含 1GB 下载） | **0.34s** | — |
| Top-5 命中（§15.6 评测） | 100% | 100% | 无变化 |
| Top-1 命中（§15.6 评测） | 94% | 88% | -6% |

### 8.2 ★ 改默认值暴露了 4 个"依赖默认配置"的脆弱测试

这是本次改动**意外但重要的收获**：改一个默认值，让 4 条测试的问题浮出水面。

| 测试 | 原状态 | 问题性质 |
| --- | --- | --- |
| `test_endpoint_reports_hybrid_rerank` | **变红** | 依赖默认开启（诚实失败，容易被发现） |
| `test_resolve_mode_with_rerank` | **变红** | 同上 |
| `test_rerank_reorders_by_scores` | **变红** | 同上 |
| `test_rerank_skipped_when_too_few_candidates` | **仍然通过** | ⚠️ **假通过**：断言 `reranker.calls == []` 因"未启用"而成立，已不再验证"候选不足时跳过" |
| `test_rerank_failure_degrades_to_rrf_order` | **仍然通过** | ⚠️ **降级分支根本没被触发**，这层保护没人看着了 |

**后两条是最危险的**：它们不会红，只会**悄悄失去防回归能力**。

**处理**：5 条全部改为**显式 monkeypatch 声明意图**（要看 rerank 生效就显式打开），并新增一条契约测试
`test_endpoint_reports_hybrid_by_default`——**同时断言默认值为 `false` 与接口报告 `hybrid`**，
这样"有人把默认值改回 true"时会立刻红，并提示同步更新评测结论。

### 8.3 教训

> **"依赖默认配置"的测试是脆弱的**：默认值一改，一部分红（好办）、一部分**静默变成无效测试**（难发现）。
> 正确做法是让每条测试**显式声明它依赖的配置状态**，而不是继承默认值。

这条经验对后续阶段同样适用——阶段 5/6 会新增更多配置开关（agent 开关、评测开关等），
新写测试时应直接遵循这个约定。
