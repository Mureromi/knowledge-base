## 1. ★ 四个实测结论（写代码前必须知道）

### 1.1 ★★ 最重要的诚实结论：rerank 在小语料上**几乎没有提升**

我做了对照实验（10 篇中文文档 → 20 个切片，检索 Top5）：

| 查询 | 关键词 Top1 | 纯向量 Top1 | 混合+RRF Top1 | **+rerank Top1** |
| --- | --- | --- | --- | --- |
| 价保（精确术语） | ✅ | ✅ | ✅ | ✅ |
| DX-7 型号的运费是多少（含噪声） | ❌ | ✅ | ✅ | ✅ |
| 我想知道东西坏了怎么办（口语化） | ❌ | ❌ | ❌ | ❌ |
| 钱什么时候退给我（口语化改写） | ❌ | ✅ | ✅ | ✅ |
| 秒杀商品降价了能赔吗 | ✅ | ✅ | ✅ | ✅ |
| **Top1 命中率** | **2/5** | **4/5** | **4/5** | **4/5** |

另一组实验（8 个查询 / 20 切片）里，**向量检索本身就已经 8/8 排在第一位**，rerank 之后仍是 8/8（其中一个查询从第 1 名被挤到第 2 名）。

**结论：在只有几十个切片的小语料上，向量检索已接近饱和，rerank 没有提升空间。** 原因是 rerank 只能**重排候选**，不能**召回**——如果正确答案根本不在候选里（上表「东西坏了怎么办」那条），rerank 无能为力。

**那不做的理由成立吗？** 不成立，但预期要调整：

| rerank 真正有用的场景 | 你的项目现状 |
| --- | --- |
| 语料规模上千切片，候选池里挤进大量"相似但不相关"的片段 | 目前是个位数～几十个切片 |
| 候选有 20-50 个需要精选到 5 个 | 现在是 20 个里选 5 个，向量排序已经准 |
| 存在"表述相近、主题不同"的干扰项 | 取决于你的文档集 |

**所以本阶段的正确做法是**：把混合检索 + rerank 的**架构**搭好（这是正确的架构），但**必须在自己的真实文档集上测出 rerank 的增量**再决定是否长期保留这个 1GB 的模型。测试方法见 §9.5。

> **这是一个"架构正确 ≠ 立即有收益"的典型案例。** 很多 RAG 教程会直接说"必须加 rerank"，但不说它什么时候才有用。**在只有几十个切片时加 rerank，付出 1GB 内存和 55ms 延迟，换来 0 提升。** 先把架构搭对，用数据决定是否启用。

### 1.2 ★ rerank 本身很快，瓶颈在模型体积

| 指标 | 实测 |
| --- | --- |
| rerank 6 个候选 | **33ms**（约 **6ms/候选**） |
| rerank 10 个候选（本阶段默认） | ≈ 60ms |
| `bge-reranker-base` 体积 | **1.04GB** |
| 两个模型合计磁盘 | ≈ 1.2GB（含 ONNX 与元数据） |

**延迟完全可接受**（相对 LLM 的 500-2000ms 而言），**体积才是代价**。

### 1.3 ★★ 新的下载坑：`huggingface_hub` 的 Xet 后端在镜像上 401

阶段 4 前置验证时配了 `HF_ENDPOINT=https://hf-mirror.com` 就能下载。**但这次下载 reranker 时失败了**：

```
RuntimeError: Task error: File reconstruction error: CAS Client Error:
HTTP status client error (401 Unauthorized),
domain: https://cas-server.xethub.hf.co/v2/reconstructions/...
```

**根因**：`huggingface_hub 1.33.0` 默认把文件下载**路由到 Xet 存储后端**（`cas-server.xethub.hf.co`），而 **hf-mirror 不支持这个接口**，于是 401。这不是镜像挂了，是新版 hub 的下载路径变了。

**解法：禁用 Xet**（实测有效，14 秒完成下载）：

```bash
export HF_HUB_DISABLE_XET=1
```

```python
# 代码里也要设（必须在 import huggingface_hub 之前执行）
import os

os.environ.setdefault("HF_HUB_DISABLE_XET", "1")
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
```

**所以阶段 4 的三个下载相关环境变量缺一不可**：

| 变量 | 作用 | 不设的后果 |
| --- | --- | --- |
| `HF_ENDPOINT=https://hf-mirror.com` | 走国内镜像 | huggingface.co 连不通（HTTP 000） |
| `HF_HUB_DISABLE_XET=1` | 禁用 Xet 后端 | 401 Unauthorized |
| `cache_dir=...` | 模型持久化目录 | 落在系统临时目录，重启重新下载 |

### 1.4 pgvector 用法要点

已实测（pgvector 0.8.7）：

| 项 | 说明 |

### 2.3 ★ 内存预算（本机实测）

阶段 4 引入两个本地模型，**内存是本阶段最大的资源代价**。以下全部是实测（macOS / Apple Silicon / Python 3.14.5）：

#### 2.3.1 逐项实测

| 环节 | 累计 RSS | 增量 |
| --- | --- | --- |
| 空 Python 进程 | 14 MB | — |
| + `import app.main`（fastapi / sqlalchemy / redis / arq 全部依赖） | **92 MB** | +78 MB |
| + **embedder**（bge-small-zh-v1.5 加载并推理） | **363 MB** | **+271 MB** |
| + **reranker**（bge-reranker-base 加载并推理） | **1164 MB** | **+801 MB** |

> ⚠️ **更正一个我之前给过的数字**：选型验证阶段我报过"进程峰值 813MB"。那是**一次性脚本**的峰值（含下载、临时结构等开销），不代表服务常驻占用。**真实服务里含 embedder 只需 363MB**（含应用栈）。以本节数字为准。

#### 2.3.2 进程分布方案（推荐）

两个进程都不要盲目加载两个模型：

| 进程 | 需要做什么 | 需要的模型 | 实测 RSS |
| --- | --- | --- | --- |
| **web**（uvicorn） | 检索时把 query 向量化、对候选精排 | embedder **+** reranker | ≈ **1.16 GB** |
| **worker**（arq） | 解析后把切片向量化（rerank 用不到） | **仅 embedder** | ≈ **363 MB** |
| **合计** | | | ≈ **1.52 GB** |

**为什么 web 必须加载 embedder**：query 向量化在请求关键路径上（每问一次就要编码一次），走跨进程调用会引入 IPC 往返，得不偿失（单条 query 编码只要 1.3ms，而 IPC 至少几毫秒）。

**为什么 worker 不需要 reranker**：worker 只做"文档 → 切片 → 向量入库"，rerank 是查询时的事，与 worker 无关。

**⚠️ 但要注意：当前 `search()` 是在 web 进程里跑的**，所以 web 加载 reranker 无法回避——除非把 rerank 挪到 worker（不建议，会给每次问答加一次 IPC）。这也是下面"降级选项"里 `RERANK_ENABLED=false` 最划算的原因。

#### 2.3.3 如果内存吃紧（降级选项）

| 选项 | 省多少 | 代价 |
| --- | --- | --- |
| **`RERANK_ENABLED=false`** | **-801 MB**（web 回到 363MB） | 按 §1.1 的实测，小语料下**几乎没有质量损失**——这是最划算的一档 |
| 换 `BAAI/bge-reranker-v2-m3-int8`（模型文件 0.57GB） | 约 -400 MB | 量化精度略降，需实测 |
| web 不加载模型，query 编码转发给 worker | web -271 MB | 每次问答多一次 IPC，实现复杂度上升，**不建议** |

**推荐的演进路线**：先按 §2.3.2 跑起来 → 用 §9.5 测出 rerank 的真实增量 → 如果增量不明显（**按 §1.1 的实测，很可能是这个结果**），直接 `RERANK_ENABLED=false`，**白拿回 801MB 内存**。

> **内存这件事不该靠猜。** 上面每个数字都是 `resource.getrusage(RUSAGE_SELF).ru_maxrss` 实测的。你换机器或换模型后应该重测一次，命令见 §2.3.4。

#### 2.3.4 怎么自己复测


## 3. 数据模型

### 3.1 `chunks` 加向量列

```python
# app/models/chunk.py 追加
from pgvector.sqlalchemy import Vector

# ★ 维度必须与 embedding 模型一致（bge-small-zh-v1.5 = 512）
#   维度写错不会在写入时报错，只会在查询时报"different vector dimensions" —— 很难排查
embedding: Mapped[list[float] | None] = mapped_column(
    Vector(settings.embedding_dim), nullable=True
)
```

**为什么可空**：回填是异步的过程；可空能让"加列 → 回填"两步分开做，中途服务仍可用（无向量的切片仍能被关键词召回）。

### 3.2 迁移（PostgreSQL 必需，SQLite 不支持）

```python
# migrations/versions/xxxx_phase4_chunk_embedding.py
def upgrade() -> None:
    if _is_sqlite():
        # SQLite 没有 vector 类型。测试用内存库，跳过即可（模型层已是 Vector，
        # 但 SQLite 不认，所以测试环境走 create_all 时会失败 —— 见 §9.1 的处理）
        return
    op.execute("CREATE EXTENSION IF NOT EXISTS vector")   # ★ 幂等，缺了就建
    op.add_column("chunks", sa.Column("embedding", Vector(512), nullable=True))


def downgrade() -> None:
    if _is_sqlite():
        return
    op.drop_column("chunks", "embedding")
```

> **迁移里显式 `CREATE EXTENSION`**：虽然本机已手动建过，但写在迁移里能保证**任何新环境**（换机器、CI、别人的电脑）一条 `alembic upgrade head` 就够，不用额外记得跑一句 SQL。这是可复现性的一部分。

### 3.3 查询改写缓存

改写要调 LLM，同一问题在同一会话里可能重复出现，值得缓存：

```
kb:v2:rewrite:{sha256(owner_id | session_id | 问题 | 窗口指纹)}
```

**键里为什么带窗口指纹**：同一个「那退货呢？」在不同上下文里指的可能是不同东西，改写结果必须随上下文变化。TTL 用 `query_rewrite_cache_ttl`（1 小时）。

复用阶段 1 的 `CacheBackend` 抽象，不新增基础设施。

## 4. 查询改写（多轮追问的关键）

### 4.1 为什么必须有这一步

阶段 2 引入了滑动窗口，用户可以追问。但**向量检索无法处理指代和省略**：

| 用户输入 | 向量检索会怎样 |
| --- | --- |
| 「那退货呢？」 | 向量化后语义模糊，检索到什么都可能 |
| 「它多久到账？」 | 「它」无线索，基本随机 |
| 「退款要多久到账？」（自包含） | 正常 |

阶段 2 的**关键词**检索对这类追问也不是完全失效（2-gram 能匹配到「退货」两字），但换成向量后，**语义被稀释反而更差**。

### 4.2 实现

```python
# app/services/query_rewrite.py
"""把多轮追问改写成自包含的检索句。

★ 为什么必须做（阶段 4 §4.1）：向量检索无法处理指代与省略。
   「那退货呢？」单看这句根本没法定向量，必须结合上文补全。

★ 为什么用 LLM 而不是拼接历史（对比见 §4.3）。
"""

import hashlib
import logging

from sqlalchemy.ext.asyncio import AsyncSession

from app.clients.cache import CacheBackend
from app.clients.llm import LLMClient
from app.core.config import settings

logger = logging.getLogger(__name__)

REWRITE_SYSTEM_PROMPT = """你是一个检索查询改写器。根据对话历史，把用户最新的一句话改写成一个**自包含的检索查询**。

规则：
1. 只输出改写后的查询语句本身，不要解释、不要加引号、不要加任何前缀。
2. 补全指代和省略的信息（「它」「那个」「那…呢」要还原成具体对象）。
3. 保留原句里的关键术语（型号、订单号、专有名词），不要替换成同义词。
4. 如果原句本身已经自包含，原样输出。
5. 改写后的查询不超过 60 字。

示例：
历史：用户问「退款要多久到账？」助手答「审核通过后 5-7 个工作日。」
输入：那退货呢？
输出：退货的条件和流程是什么
"""


async def rewrite_query(
    db: AsyncSession,
    llm: LLMClient,
    cache: CacheBackend,
    *,
    owner_id: int,
    session_id: int | None,
    question: str,
    window: list[dict[str, str]],
) -> str:
    """返回用于检索的查询句。无会话或无需改写时原样返回 question。"""
    if not settings.query_rewrite_enabled or not window:
        # 没有历史 = 首轮 = 问题本身自包含，直接返回（省一次 LLM 调用）
        return question

    history = window[-(settings.query_rewrite_max_history_turns * 2):]
    fingerprint = hashlib.sha256(
        (
            f"{owner_id}|{session_id}|{question}|"
            + "|".join(f"{m['role']}:{m['content']}" for m in history)
        ).encode()
    ).hexdigest()[:32]
    key = f"{settings.cache_key_prefix}:v2:rewrite:{fingerprint}"

    cached = await cache.get_json(key)
    if cached and cached.get("query"):
        return str(cached["query"])

    messages = [
        {"role": "system", "content": REWRITE_SYSTEM_PROMPT},
        *history,
        {"role": "user", "content": question},
    ]
    try:
        result = await llm.chat(messages, temperature=0.0, max_tokens=100)
        rewritten = result.content.strip().strip("「」\"'").splitlines()[0][:200]
    except Exception as exc:                       # noqa: BLE001
        # ★ 改写失败不能让问答失败：退化为原问题（检索质量略降，但服务可用）
        logger.warning("查询改写失败，退化为原问题: %s", exc)
        return question

    if not rewritten:
        return question

    await cache.set_json(
        key, {"query": rewritten}, ttl=settings.query_rewrite_cache_ttl
    )
    logger.info(
        '{"event":"query_rewrite","user":%s,"raw_len":%s,"rewritten":"%s"}',
        owner_id, len(question), rewritten[:60],
    )
    return rewritten
```

### 4.3 为什么选 LLM 改写而不是拼接历史

| 方案 | 检索质量 | 成本 | 取舍 |
| --- | --- | --- | --- |
| **LLM 改写**（选用） | ✅ 高：指代被真正补全 | 每轮追问 +1 次 LLM 调用（≈0.0002 元、约 300ms） | 多一次调用，但缓存后重复问题不再花钱 |
| 拼接最近历史 | ⚠️ 中：**向量会被无关内容稀释** | 零额外调用 | 便宜但效果差——把「退款到账」的历史拼进「退货」的查询里，两者语义互相干扰 |
| 不处理 | ❌ 低：追问基本检索不到 | 零 | 「那退货呢？」这类输入直接失效 |

**注意改写只影响检索，不影响回答**：`build_messages` 里发给 LLM 的仍是**原始问题 + 真实会话历史**，改写句只用于去数据库捞切片。这一点很容易写错——如果把改写句也当成提问发给模型，用户会看到答非所问。

### 4.4 代价与降级

- **额外延迟**：约 300ms（实测参考：短 prompt 非思考模式 500-900ms，改写只有 100 token 上限，更快）
- **额外成本**：约 0.0002 元/次，**命中缓存后为 0**
- **失败降级**：改写抛异常时**返回原问题**，绝不因此让问答失败
- **首轮不调用**：`window` 为空时直接返回原问题（首轮问题天然自包含）

### 5.1 流水线

```
                    question（原始）
                          │
                          ▼
              ┌───────────────────────┐
              │ ① 查询改写（仅多轮）    │ LLM，带缓存；失败降级为原问题
              └───────────┬───────────┘
                          ▼ resolved_query

  │ 2-gram ILIKE  │               │ pgvector <#>  │
  │ Top-20        │               │ Top-20        │
  └───────┬───────┘               └───────┬───────┘
          └───────────────┬───────────────┘
                          ▼
              ┌───────────────────────┐
              │ ③ RRF 融合            │ score = Σ 1/(k + rank)
              └───────────┬───────────┘
                          ▼ 候选（去重后按 RRF 分排序）
              ┌───────────────────────┐

                  最终 Top-5 进上下文
```

### 5.2 实现（`app/services/retrieval.py` 重写）

```python
"""检索层。阶段 4：关键词 + 向量 → RRF 融合 → rerank。

★ 签名保持不变（`search(db, owner_id=..., question=..., top_k=...)`），
  这样 qa.py 只需要多传一个 resolved_query，其余逻辑不动 —— 这是阶段 0 就定下的
  "换实现不换签名"约定的兑现。
"""

from dataclasses import dataclass

from sqlalchemy import or_, select
from sqlalchemy.ext.asyncio import AsyncSession

from app.clients.embedding import EmbeddingClient
from app.clients.rerank import RerankClient
from app.core.config import settings
from app.models.chunk import Chunk
from app.models.document import Document


@dataclass
class RetrievedChunk:
    chunk_id: int
    document_id: int
    document_title: str
    seq: int
    content: str
    score: float = 0.0
    # 阶段 4 新增：便于排查"这条是靠关键词还是向量召回的"
    keyword_rank: int | None = None
    vector_rank: int | None = None


async def _keyword_candidates(
    db: AsyncSession, *, owner_id: int, query: str, limit: int
) -> list[tuple[int, float]]:
    """关键词召回。返回 [(chunk_id, 命中关键词数)]，按命中数降序。"""
    tokens = _keywords(query)
    if not tokens:
        return []
    stmt = (
        select(Chunk.id, Chunk.content)
        .join(Document, Document.id == Chunk.document_id)
        .where(Chunk.owner_id == owner_id)
        .where(Document.status == "ready")          # ★ 阶段 3 的约定：只检索 ready
        .where(or_(*[Chunk.content.ilike(f"%{t}%") for t in tokens]))
        .limit(limit * 4)
    )
    rows = (await db.execute(stmt)).all()
    scored = [
        (int(cid), float(sum(1 for t in tokens if t in content)))
        for cid, content in rows
    ]
    scored.sort(key=lambda x: (-x[1], x[0]))
    return scored[:limit]


async def _vector_candidates(
    db: AsyncSession,
    embedder: EmbeddingClient,
    *,
    owner_id: int,
    query: str,
    limit: int,
) -> list[tuple[int, float]]:
    """向量召回。返回 [(chunk_id, 相似度)]，按相似度降序。

    ★ 只召回 embedding 非空的切片：回填期间新旧混存，NULL 会被 SQL 的 ORDER BY 排到最后，
      显式过滤更清晰。
    """
    # ★ query 侧加指令前缀（文档侧不加）—— 阶段 4 前置实测：区分度 +64%
    query_vec = await embedder.embed_query(query)
    stmt = (
        select(Chunk.id, Chunk.embedding.max_inner_product(query_vec).label("sim"))
        .join(Document, Document.id == Chunk.document_id)
        .where(Chunk.owner_id == owner_id)
        .where(Document.status == "ready")
        .where(Chunk.embedding.is_not(None))
        .order_by(Chunk.embedding.max_inner_product(query_vec))
        .limit(limit)
    )
    rows = (await db.execute(stmt)).all()
    return [(int(cid), float(sim)) for cid, sim in rows]


def rrf_fuse(
    ranked_lists: list[list[int]], *, k: int | None = None
) -> list[tuple[int, float]]:
    """Reciprocal Rank Fusion：score(d) = Σ 1/(k + rank_i(d))。

    为什么用 RRF 而不是加权分数：关键词得分（命中个数）与向量相似度量纲完全不同，
    直接加权需要归一化和调参；RRF 只用**名次**，天然免调参、对量纲不敏感。
    k=60 来自原论文（Cormack et al. 2009），作用是压低头部名次的权重差。

    ★ 这是本阶段最值得记住的一个"少调参"技巧。
    """
    k = k or settings.rrf_k
    agg: dict[int, float] = {}
    for lst in ranked_lists:
        for rank, cid in enumerate(lst, start=1):
            agg[cid] = agg.get(cid, 0.0) + 1.0 / (k + rank)
    return sorted(agg.items(), key=lambda kv: (-kv[1], kv[0]))


async def _load_chunks(
    db: AsyncSession, chunk_ids: list[int]
) -> dict[int, tuple[Chunk, str]]:
    """批量取切片 + 文档标题（一次查询，避免 N+1）。"""
    if not chunk_ids:
        return {}
    stmt = (
        select(Chunk, Document.title)
        .join(Document, Document.id == Chunk.document_id)
        .where(Chunk.id.in_(chunk_ids))
    )
    return {c.id: (c, title) for c, title in (await db.execute(stmt)).all()}


async def search(
    db: AsyncSession,
    *,
    owner_id: int,
    question: str,
    top_k: int | None = None,
    embedder: EmbeddingClient | None = None,
    reranker: RerankClient | None = None,
) -> list[RetrievedChunk]:
    """混合检索主入口。签名与阶段 0 保持一致（新增可选依赖参数）。

    embedder / reranker 允许为 None：便于测试注入假实现，也便于"临时关掉向量"对比效果。
    """
    final_k = top_k or settings.final_top_k

    # ---------- ① 两路召回（可并发）----------
    keyword_pairs = await _keyword_candidates(
        db, owner_id=owner_id, query=question, limit=settings.keyword_top_k
    )
    vector_pairs: list[tuple[int, float]] = []
    if settings.embedding_enabled and embedder is not None:
        vector_pairs = await _vector_candidates(
            db, embedder, owner_id=owner_id, query=question, limit=settings.vector_top_k
        )

    if not keyword_pairs and not vector_pairs:
        return []

    # ---------- ② RRF 融合 ----------
    fused = rrf_fuse(
        [[cid for cid, _ in keyword_pairs], [cid for cid, _ in vector_pairs]]
    )
    kw_rank = {cid: i for i, (cid, _) in enumerate(keyword_pairs, start=1)}
    vec_rank = {cid: i for i, (cid, _) in enumerate(vector_pairs, start=1)}

    # ---------- ③ rerank（只对前 N 个）----------
    head = fused[: settings.rerank_top_k]
    tail = fused[settings.rerank_top_k :]

    if (
        settings.rerank_enabled
        and reranker is not None
        and len(head) >= settings.rerank_min_candidates
    ):
        loaded = await _load_chunks(db, [cid for cid, _ in head])
        docs = [loaded[cid][0].content for cid, _ in head if cid in loaded]
        ids = [cid for cid, _ in head if cid in loaded]
        if docs:
            scores = await reranker.rerank(question, docs)
            reranked = [
                (ids[i], float(scores[i])) for i in sorted(
                    range(len(ids)), key=lambda i: -scores[i]
                )
            ]
            head = reranked
            # rerank 分数量纲与 RRF 不同，尾部保留 RRF 分（仅作补充，通常用不到）
    # ---------- ④ 组装 ----------
    ordered = head + tail
    ordered = ordered[: max(final_k, settings.rerank_top_k)]
    loaded = await _load_chunks(db, [cid for cid, _ in ordered])

    results: list[RetrievedChunk] = []
    for cid, score in ordered:
        item = loaded.get(cid)
        if item is None:
            continue
        chunk, title = item
        results.append(
            RetrievedChunk(
                chunk_id=chunk.id,
                document_id=chunk.document_id,
                document_title=title,
                seq=chunk.seq,
                content=chunk.content,
                score=score,
                keyword_rank=kw_rank.get(cid),
                vector_rank=vec_rank.get(cid),
            )
        )
        if len(results) >= final_k:
            break
    return results
```

> **`_keywords` 与阶段 0 完全一致**（中文 2-gram + 英文分词），无需改动——它现在是"两路召回中的一路"，而不是唯一手段。

### 5.3 与 `qa.py` 的接线

`qa.py` 只需要两处小改动：

```python
# 1) 改写查询（在检索之前）
resolved = await rewrite_query(
    db, llm, cache,
    owner_id=owner_id, session_id=session_id,

# 2) 用改写后的查询去检索；但**发给 LLM 的仍是原始 question**
```

**缓存键必须跟着改**：现在检索依赖 `resolved`，所以缓存键要么用它、要么把原始问题与窗口指纹一起算进去（现有实现已经包含窗口指纹，所以**沿用原问题即可**——只要同一窗口内改写结果稳定）。

> ⚠️ 这里有个容易忽略的点：**改写结果本身也被缓存了**，所以同一窗口 + 同一问题的 `resolved` 是稳定的，缓存键不会因为改写引入不确定性。**如果改写没缓存，缓存键就会漂移，阶段 1 的答案缓存会大面积失效。** 这是两个缓存机制之间的耦合，必须记住。

### 6.2 `app/clients/rerank.py`

```python
"""Rerank 客户端：cross-encoder 精排。

与 embedding 的三点不同：
1. 输入是 (query, 候选文档) 对，输出是相关性分数（不是向量）
2. 必须成对计算，N 个候选就是 N 次推理 —— 所以只对 Top-K 精排，不能全量
3. 分数无固定范围（本模型实测约 -11 ~ +5），只能用于**排序**，不能当阈值
"""

import asyncio
import logging
import os

from app.core.config import settings

logger = logging.getLogger(__name__)


class RerankClient:
    def __init__(self) -> None:
        self._model = None

    def startup(self) -> None:
        """加载模型（约 1GB，首次较慢）。在 lifespan 里调一次。"""
        os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
        os.environ.setdefault("HF_HUB_DISABLE_XET", "1")
        from fastembed.rerank.cross_encoder import TextCrossEncoder

        self._model = TextCrossEncoder(
            model_name=settings.rerank_model,
            cache_dir=settings.embedding_cache_dir,   # 与 embedding 共用缓存目录
        )
        logger.info("rerank 模型已加载: %s", settings.rerank_model)

    async def rerank(self, query: str, documents: list[str]) -> list[float]:
        """返回与 documents 等长的相关性分数。同步 CPU 活 → 线程池。"""
        if not documents:
            return []
        return await asyncio.to_thread(self._rerank_sync, query, documents)

    def _rerank_sync(self, query: str, documents: list[str]) -> list[float]:
        assert self._model is not None, "模型未加载：请在 lifespan 中调用 startup()"
        # fastembed 的 rerank 是生成器，逐个产出分数，顺序与输入一致
        return [float(s) for s in self._model.rerank(query, documents)]


rerank_client = RerankClient()


async def get_reranker() -> RerankClient:
    """FastAPI 依赖；测试用 dependency_overrides 注入假实现。"""
    return rerank_client
```

> **分数范围要小心**：实测某次 rerank 输出是 `[0.57, -10.19, -10.19, -10.2]`——**分数是 logit 经 sigmoid 后的值，负值表示"极不相关"，但不代表错误**。所以**只能用于排序，绝不能像向量相似度那样设阈值**（比如"低于 0.3 就丢弃"会把所有负分全丢掉）。如果要过滤，应该用**向量相似度**设阈值（阶段 4 前置报告实测：相关问题 0.59-0.67、不相关问题 0.19-0.31，可分界在 0.45）。

## 7. 回填与索引

### 7.1 回填脚本（幂等）

```python
# scripts/backfill_embeddings.py
"""为 chunks 补算 embedding。

用法：
    .venv/bin/python scripts/backfill_embeddings.py --dry-run
    .venv/bin/python scripts/backfill_embeddings.py --batch-size 32

★ 幂等：只处理 embedding IS NULL 的行。中断、超时、模型下载失败后重跑都安全，
  不会重算已成功的行，也不会产生重复数据。

★ 为什么必须幂等：回填可能因为各种原因中途停止（模型 1GB 要下载、某批编码抛异常、
  被 Ctrl-C）。"再跑一次"必须是安全的——这是所有数据修复脚本的基本要求。
"""

from __future__ import annotations

import argparse
import asyncio
import os
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from sqlalchemy import func, select, update

from app.core.config import settings
from app.db.session import SessionLocal, engine
from app.models.chunk import Chunk


async def backfill(*, dry_run: bool, batch_size: int, document_id: int | None) -> None:
    # 必须在 import fastembed 之前设好（§1.3）
    os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
    os.environ.setdefault("HF_HUB_DISABLE_XET", "1")

    from fastembed import TextEmbedding

    async with SessionLocal() as db:
        total = int((await db.scalar(select(func.count(Chunk.id)))) or 0)
        pending_stmt = select(func.count(Chunk.id)).where(Chunk.embedding.is_(None))
        if document_id is not None:
            pending_stmt = pending_stmt.where(Chunk.document_id == document_id)
        pending = int((await db.scalar(pending_stmt)) or 0)

    print(f"切片总数: {total}  待回填: {pending}  批大小: {batch_size}")
    if pending == 0:
        print("✅ 没有待回填的切片（幂等：重跑安全）")
        return
    if dry_run:
        print("DRY-RUN：未写入。去掉 --dry-run 实际执行。")
        return

    model = TextEmbedding(
        model_name=settings.embedding_model,
        cache_dir=settings.embedding_cache_dir,
    )
    print(f"模型已加载: {settings.embedding_model}（维度 {settings.embedding_dim}）")

    done = 0
    while True:
        # ★ 每批一个事务：不要整表一个大事务（几百页会长时间持锁）
        async with SessionLocal() as db:
            stmt = select(Chunk.id, Chunk.content).where(Chunk.embedding.is_(None))
            if document_id is not None:
                stmt = stmt.where(Chunk.document_id == document_id)
            rows = (await db.execute(stmt.limit(batch_size))).all()
            if not rows:
                break

            ids = [int(r[0]) for r in rows]
            texts = [r[1] for r in rows]

            # ★ 文档侧不加指令前缀（只有 query 加，见 §1.4）
            # ★ 同步 CPU 活在 to_thread 里跑（阶段 3 §1 的同一原则）
            vectors = await asyncio.to_thread(
                lambda: [v.tolist() for v in model.embed(texts)]
            )

            for cid, vec in zip(ids, vectors, strict=True):
                await db.execute(
                    update(Chunk).where(Chunk.id == cid).values(embedding=vec)
                )
            await db.commit()
            done += len(ids)
            pct = 100.0 * done / max(pending, 1)
            print(f"  已回填 {done}/{pending}（{pct:.1f}%）")

    print(f"\n✅ 回填完成，共处理 {done} 个切片")


def main() -> None:
    ap = argparse.ArgumentParser(description="为 chunks 补算 embedding（幂等）")
    ap.add_argument("--dry-run", action="store_true", help="只统计不写入")
    ap.add_argument("--batch-size", type=int, default=32)
    ap.add_argument("--document-id", type=int, default=None, help="只回填某个文档")
    a = ap.parse_args()
    try:
        asyncio.run(
            backfill(dry_run=a.dry_run, batch_size=a.batch_size, document_id=a.document_id)
        )
    finally:
        asyncio.run(engine.dispose())


if __name__ == "__main__":
    main()
```

**四个设计要点**：

| # | 要点 | 为什么 |
| --- | --- | --- |
| 1 | `WHERE embedding IS NULL` | 幂等；中断后重跑只处理剩余的 |
| 2 | 每批一个事务 | 整表一个事务会长时间持锁，几百页文档时阻塞其他写入 |
| 3 | 不调 `embed_query`（不加前缀） | 文档侧加指令前缀**会降低**检索效果（前缀是给 query 用的） |
| 4 | `asyncio.to_thread` 包装编码 | 编码是同步 CPU 活，直接 await 会阻塞事件循环 |

> **新增切片不需要跑这个脚本**：worker 在解析入库时就该直接写向量（§5.3）。回填只用于**历史数据**和**换 embedding 模型后重算**。

### 7.2 回填验收

```sql
-- 回填进度
SELECT
  count(*) AS 总切片,
  count(embedding) AS 已向量化,
  round(100.0 * count(embedding) / nullif(count(*), 0), 1) AS 完成百分比
FROM chunks;
```

### 7.3 ★ 为什么本阶段**不建**向量索引

| 数据量 | 建议 |
| --- | --- |
| < 1 万行 | **顺序扫描，不建索引**（本阶段） |
| > 1 万行 | 考虑 `hnsw`（比 `ivfflat` 召回率更稳） |

**两个理由**：

1. **`ivfflat`/`hnsw` 都需要调参**（`lists`/`m`/`ef_construction`）。参数不对会**降低召回率**——你花了力气加向量，结果因为索引没调好而召回变差，很难排查。
2. **顺序扫描在这个规模下更快也更准**（100% 召回）。性能优化必须由**实测瓶颈**驱动，而不是"应该建索引"的直觉。

> 这条和第 1.1 节的 rerank 结论是同一种思维：**先让架构正确，再用实测数据决定是否加优化层**。RAG 里最容易犯的错就是照搬教程里的"标准配置"，而没有验证它在自己的数据规模上是否成立。

## 8. 接口契约变化

| 字段 | 阶段 3 | 阶段 4 |
| --- | --- | --- |
| `retrieval_mode` | `"keyword"` | **`"hybrid"`**（rerank 开启时 `"hybrid+rerank"`） |
| `citations[].score` | 关键词命中数（整数） | RRF 分或 rerank 分（浮点，**跨模式不可比**） |
| `citations[].keyword_rank` / `vector_rank` | — | 新增，便于排查召回来源 |

**`retrieval_mode` 这个字段从阶段 0 就预留了，现在兑现**：你可以在同一个接口上对比 `keyword` / `hybrid` 的效果差异，这是简历上"召回率从 X 到 Y"那行字的直接证据来源。

> ⚠️ `score` 的语义变了，前端不要拿它做阈值判断（阶段 3 时它是"命中关键词个数"，现在是浮点融合分）。

## 9. 测试策略

### 9.1 ★ 测试环境的向量列问题（必须先解决）

`Vector(512)` 是 PostgreSQL 专属类型，**SQLite 不认识**。而现有测试全部跑在内存 SQLite 上（133 个用例），直接加列会让**所有测试在 `create_all` 阶段就崩**。

三种解法：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **A. 测试时把列类型替换成 JSON**（推荐） | 用 SQLAlchemy 的 `TypeDecorator` 或在 `conftest` 里对 `Chunk.embedding` 做类型映射 | 测试全留 SQLite，快且无需服务；代价是需要一点类型层面的技巧 |
| B. 测试也跑 PostgreSQL | `conftest` 连一个测试库 | 最真实；代价是测试依赖 PG 服务、变慢、需清理 |
| C. 测试里删掉该列 | `create_all` 前从 metadata 移除 | 简单但**测试与生产 schema 不一致**，掩盖问题 |

**推荐 A**，并在 `conftest.py` 里显式注释这是刻意的类型适配，不是 hack。

方案 A 的具体做法（在 `app/tests/conftest.py` 里，`create_all` 之前执行）：

```python
# conftest.py —— 让 SQLite 也能建出带向量列的表
from sqlalchemy import JSON
from pgvector.sqlalchemy import Vector

def _make_vector_sqlite_compatible() -> None:
    """把 Vector 列在测试用的 SQLite 上降级为 JSON 存储。

    ★ 这是刻意的类型适配，不是 hack：
      Vector(512) 是 PostgreSQL 专属类型，SQLite 不认识，直接 create_all 会报
      "CompileError: can't render element of type VECTOR"。
      测试关注的是**检索逻辑**（RRF 融合、降级、状态过滤），不是 pgvector 本身；
      向量距离计算由 PostgreSQL 负责，本就无法在 SQLite 上断言。
      所以测试里把向量当"普通列表"存取，检索路径通过**假 embedder + 应用层排序**验证。
    """
    from app.models.chunk import Chunk

    Chunk.__table__.c.embedding.type = JSON()


@pytest_asyncio.fixture
async def test_engine():
    _make_vector_sqlite_compatible()      # ← 必须在 create_all 之前
    engine = create_async_engine("sqlite+aiosqlite://", ...)
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    ...
```

**这个方案的边界要说清楚**：它让"带向量列的 schema 能在 SQLite 上建起来"，
但**SQLite 上无法验证真实的向量距离排序**（`<#>` 是 PG 算子）。
所以：

| 验证目标 | 在哪测 |
| --- | --- |
| RRF 融合、降级逻辑、状态过滤、改写缓存 | ✅ SQLite（假 embedder + 应用层） |
| **真实的 pgvector 距离排序与算子** | ✅ 手工/集成测试（连真实 PG，见 §9.6） |


> 这是阶段 4 引入的第一个"数据库能力差异"问题。如果将来还要用 PG 专属特性（`JSONB`、全文检索 `tsvector`、部分索引），会反复遇到，值得把方案做成一个通用夹具。

### 9.3 假客户端的注入方式

```python
# conftest.py 新增
class FakeEmbedder:
    """可编程假 embedder：按文本返回预设向量，便于精确控制召回顺序。"""
    def __init__(self, vectors: dict[str, list[float]] | None = None, dim: int = 512):
        self.vectors = vectors or {}
        self.dim = dim
        self.query_calls: list[str] = []

    async def embed_query(self, text: str) -> list[float]:
        self.query_calls.append(text)
        return self.vectors.get(text, [0.0] * self.dim)

    async def embed_documents(self, texts: list[str]) -> list[list[float]]:
        return [self.vectors.get(t, [0.0] * self.dim) for t in texts]


class FakeReranker:
    """可编程假 reranker：按 (query, doc) 返回预设分数。"""
    def __init__(self, scores: dict[tuple[str, str], float] | None = None):
        self.scores = scores or {}
        self.calls: list[tuple[str, list[str]]] = []

    async def rerank(self, query: str, documents: list[str]) -> list[float]:
        self.calls.append((query, documents))
        return [self.scores.get((query, d), 0.0) for d in documents]
```

### 9.4 一个必须注意的测试陷阱

**假 embedder 返回全零向量时，向量排序是任意的**（所有距离相同）。写断言时要么给不同向量，要么断言"顺序稳定"而不是"顺序正确"。否则测试会随机红绿——**这是向量相关测试最常见的 flaky 来源**。

### 9.5 ★ rerank 增量评测（本阶段必须做的一次）

因为 §1.1 已证明"rerank 在小语料上可能零提升"，所以**必须用真实数据测一次增量**，再决定是否长期保留这个 1GB 模型：

```bash
# 准备 10-20 个真实问题 + 期望命中的文档（写进 app/evals/rerank_cases.yaml）
# 然后跑两次：RERANK_ENABLED=false / true，对比 Top-1 与 Top-5 命中率
```

| 结果 | 决策 |
| --- | --- |
| rerank 提升 ≥ 10% 的 Top-1 命中 | 保留，`RERANK_ENABLED=true` |
| 提升在 0-10% 之间 | 保留但记录权衡（1GB 内存换这点提升是否值得） |
| **几乎无提升**（很可能是这个结果） | **`RERANK_ENABLED=false`，代码留着**——等语料涨到上千切片再打开 |

**这个开关的价值**：让你能用数据决策，而不是靠"教程说必须加"。这也是阶段 6 评估体系的前哨。

### 9.6 一次性的 pgvector 集成验证（手工，连真实 PG）

因为 SQLite 测不了向量算子，所以要做**一次**手工验证（可写成一个 `-m pg` 标记的测试）：

```sql
-- 连真实 PG：插入三个已知向量，确认 <#> 排序符合预期
INSERT INTO chunks (document_id, owner_id, seq, content, char_count, embedding)
VALUES (:d, :u, 0, 'A', 1, '[1,0,0,...]'),   -- 与查询向量相同
       (:d, :u, 1, 'B', 1, '[0,1,0,...]'),   -- 正交
       (:d, :u, 2, 'C', 1, '[-1,0,0,...]');  -- 相反

SELECT content FROM chunks ORDER BY embedding <#> '[1,0,0,...]' LIMIT 3;
-- 期望顺序：A（内积最大 → 距离最小）、B、C
```

**这一步别省**：它是唯一能证明"Python 侧的 `max_inner_product()` 真的生成了正确的 `<#>` 查询"的方式。
如果漏了，可能出现"逻辑测试全绿、真实检索全错"的情况（比如排序方向反了）。

## 11. 风险与取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **rerank 可能白付 1GB 内存** | §1.1 实测小语料零提升 | 用 `RERANK_ENABLED` 开关 + §9.5 真实评测决定 |
| 进程内存进一步上升 | 已有 813MB（embedder），再加 reranker ≈ +1GB | 两个模型**只在 worker 里加载**；web 侧按需（embedder 必须，reranker 可只在 worker） |
| 查询改写增加延迟 | 每轮追问 +约 300ms | 改写结果缓存 1 小时；首轮不调用 |
| 改写质量不可控 | 可能改错，反而带偏检索 | 提示词限制"保留关键术语"；日志记录 raw→rewritten 便于抽查 |
| 向量列与 SQLite 不兼容 | 测试全崩（§9.1） | 类型映射夹具 |
| 回填中途中断 | 部分切片无向量 | 幂等脚本 + 关键词路兜底（无向量仍可被关键词召回） |
| `score` 语义变化 | 前端若拿它做阈值会失效 | §8 明确标注"跨模式不可比" |

### 12.1 ★ 阶段 5 的一个硬约束（提前记下，避免当天卡住）

阶段 5 要用 **DeepSeek Tool Calls**，而思考模式与 tools 有一个**容易踩死的组合约束**（阶段 0 文档已记录，这里再强调一次）：

> **请求携带 `tools` 参数时，后续所有轮次必须完整回传 `reasoning_content`，否则 API 直接返回 400。**

具体表现：
- 不带 tools：`reasoning_content` 无需回传，传了也会被忽略
- **带 tools**：历史轮次的 `reasoning_content` **必须**原样回传，且会被拼接进上下文

**为什么容易踩**：你现在的 `build_messages()`（§5.3）只构造 `{"role", "content"}` 两个字段。
Agent 场景下如果照旧构造，就会丢掉 `reasoning_content`，然后收到一个 400，
而错误信息指向的是"消息格式"而不是"你丢了 reasoning_content"，排查会绕。

**建议**：阶段 5 开工前先写一个**最小可运行的 tools 调用**验证这个约束（就像阶段 4 前置做 embedding 选型验证那样），
再动手写 agent 循环。**别把它留到 agent 循环写完才发现。**

### 13.3 刻意不动

| 文件/模块 | 为什么不动 |
| --- | --- |
| `app/services/cache_key.py` | 缓存键已含窗口指纹，**改写结果本身也被缓存**，所以 `resolved` 是稳定的（§5.3）。不需要把向量纳入键——检索结果已由 `context_fingerprint` 覆盖 |
