## 0. 阶段 1 的目标与边界

阶段 0 结束时，每次问答都是"检索 → 拼 prompt → 调 LLM → 落库"，**每次都花钱**。阶段 1 要解决三个真实问题：

| 问题 | 阶段 0 现状 | 阶段 1 方案 |
| --- | --- | --- |
| 相同问题重复提问，重复付钱 | 每次都调 LLM（实测 ≈0.00056 元/次） | **答案缓存**，命中则跳过 LLM |
| 进程内 `asyncio.Semaphore` 多 worker 下失效 | `qa.py` 里的信号量只在单进程有效 | **Redis 分布式并发控制** |
| 没有任何用量约束，一个用户能把额度打满 | 无限制 | **多级限流 + 每日配额** |

### 明确不做（留给后续阶段）

| 不做 | 归属 |
| --- | --- |
| 流式输出 SSE | 阶段 2 |
| 会话记忆（`chat_sessions` 表） | 阶段 2 |
| **语义缓存**（相似问题复用答案） | 阶段 4（需要 embedding，正好复用向量能力） |
| 异步任务队列（ARQ） | 阶段 3（那时才同时需要 Redis 和 worker） |
| Langfuse 全链路追踪 | 阶段 6 |

> **关于语义缓存的重要说明**：网上很多文章把"语义缓存"当作 Redis 缓存的标配。**阶段 1 不做，这是刻意的决定**——语义缓存需要 embedding 模型，而 embedding 是阶段 4 才引入的能力。现在硬做，你得先引入一个只为了缓存而存在的 embedding 调用，又多一个成本和故障点。**先把精确缓存做扎实并测出命中率，等阶段 4 有了向量能力再升级**，那时你会有一份真实的"精确命中率 vs 语义命中率"对比数据。

## 1. 环境：Redis 装不上怎么办（本机实测）

你机器上 **`redis-server`、`redis-cli`、`docker` 全都没有**。三条路，按推荐度排序：

### 路线 A：Homebrew 安装（推荐，最简单）

```bash
brew install redis
brew services start redis      # 开机自启；或 redis-server 前台跑
redis-cli ping                 # 期望输出 PONG
```

约 10MB，比 Docker 轻得多。

### 路线 B：Docker

```bash
docker run -d --name kb-redis -p 6379:6379 redis:7-alpine
```

若同时要 PostgreSQL（阶段 4），用 docker compose 一起管更省事。**Docker 是求职硬技能，值得在阶段 3 前后系统学一次**，但阶段 1 不必为它阻塞。

### 路线 C：先不装，用 fakeredis 跑测试（**已验证可行**）

这是本阶段一个很实用的性质：**阶段 1 的全部自动化测试都不需要真 Redis**。

已实测（Python 3.14.5）：

| 包 | 版本 | 结论 |
| --- | --- | --- |
| `redis` (redis-py) | **8.1.0** | ✅ 含 `redis.asyncio` 子模块 |
| `fakeredis` | **2.39.0** | ✅ 异步客户端可用、支持 pipeline / ZSET / SET NX EX |
| `fakeredis[lua]` | 同上 + **lupa 2.8** | ✅ **Lua `eval` 可用** |

```bash
uv add redis
uv add --group dev "fakeredis[lua]"
```

> ⚠️ **一个必须知道的坑**：`fakeredis` **默认不支持 `eval`（Lua）**，会抛 `ResponseError: unknown command 'eval'`。必须装 `fakeredis[lua]` 才会带上 `lupa`。这一点我实测踩过——如果你不装 lua extra，任何用 Lua 实现的原子限流脚本在测试里都会失败，而在真实 Redis 上却是好的，会浪费你半天时间排查。

## 3. 架构：Redis 在系统中的位置

```
                    ┌─────────────────────────────┐
   POST /chat ─────▶│  L1 频率限流（滑动窗口）      │  Redis ZSET
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │  L3 每日配额检查              │  Redis INCR + 跨天 TTL
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │  检索（SQL，始终执行）        │  PostgreSQL/SQLite
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │  ★ 缓存查询（context hash）   │  Redis STRING
                    └───────┬─────────────┬───────┘
                       命中 │             │ 未命中
                            ▼             ▼
                    直接返回答案   ┌──────────────────┐
                    （跳过 LLM）   │ L2 分布式并发控制 │ Redis INCR + Lua
                                   └────────┬─────────┘
                                            ▼
                                     调用 LLM（花钱）
                                            ▼
                                     写缓存 + 落库
```

**四层各管一件事**：L1 防刷、L3 管钱、缓存省钱、L2 保护上游并发。

## 4. ★ 核心设计：缓存键必须包含"检索结果指纹"

这是阶段 1 唯一真正需要想清楚的设计，**做错了会出现"改了文档但答案不变"的严重 bug**。

### 4.1 为什么不能用「问题」当缓存键

朴素做法是 `key = hash(question)`。**这是错的**，会在两种情况下返回错答案：

| 场景 | 后果 |
| --- | --- |
| 用户上传了新文档，答案应该变了 | 仍返回旧答案 —— **错误** |
| 用户删除了某文档，引用已经不存在 | 返回带失效引用的答案 —— **错误** |
| 同名问题在不同用户之间 | 若键里漏了 `owner_id`，**跨用户泄露数据 —— 安全事故** |

### 4.2 正确做法：缓存键 = 问题 + 实际检索到的内容指纹

```python
key = sha256(f"{owner_id}|{normalized_question}|{context_fingerprint}")
```

其中 `context_fingerprint` 是**本次检索返回的切片内容的指纹**：

```python
context_fingerprint = sha256("|".join(f"{c.chunk_id}:{sha256(c.content)}" for c in chunks))
```

**为什么这样是对的**——关键在于一个认知转变：

> **被缓存的不是"问题的答案"，而是"给定这批资料 + 这个问题的答案"。**

于是语义完全自洽：

| 情况 | 指纹是否变化 | 行为 | 是否正确 |
| --- | --- | --- | --- |
| 用户上传了与问题无关的文档 | 检索 Top-K 不变 → 不变 | 命中缓存 | ✅ 正确（答案确实没变） |
| 用户上传了相关的新文档（进入 Top-K） | 变化 | 未命中，重新生成 | ✅ 正确（答案该变了） |
| 用户删除了被引用的文档 | 变化 | 未命中 | ✅ 正确（引用失效了） |
| 另一个用户问同样的问题 | `owner_id` 不同 | 未命中 | ✅ **数据隔离** |
| 同一用户重复问同一问题 | 都不变 | **命中，省一次 LLM 调用** | ✅ 这就是收益 |

**这个设计的额外好处：不需要任何显式的缓存失效逻辑。** 你不需要在"上传文档"和"删除文档"的地方加 `cache.invalidate(...)`——指纹变了，旧缓存自然永远不会再被命中，靠 TTL 自动清理。**这是把失效问题从"写路径"转移到"读路径"，是缓存设计的经典手法，也避免了一类常见的 bug（忘记失效）。**

### 4.3 代价：缓存命中仍然要查一次数据库

检索（十几毫秒的 SQL）**无法被跳过**，因为要先拿到 chunks 才能算指纹。

这是**刻意的取舍**：省掉的是 800ms + 0.00056 元的 LLM 调用，保留的是 15ms 的数据库查询。**用 15ms 换 800ms，这笔账非常划算。** 而且这样设计还有个附带好处：**缓存永远不会返回与当前检索结果不一致的答案**。

> 什么时候这种设计会失效？当检索本身变成瓶颈时（阶段 4 引入向量检索后，检索会从 15ms 涨到 50-100ms）。到那时再考虑「问题哈希 → 指纹」的两级缓存，用一次 Redis 查询跳过检索。**阶段 1 不要提前优化**。

### 4.4 缓存条目结构

用**单个 JSON 字符串**存储，不用 Hash 结构。原因：Redis 7.4 之前 Hash 的字段级 TTL 需要额外命令，而且本项目每次都是整体读写，Hash 没有优势。

```json
{
  "answer": "审核通过后，款项将在 5-7 个工作日退回原支付渠道。[1]",
  "chunk_ids": [17],
  "prompt_tokens": 199,
  "completion_tokens": 20,
  "cached_tokens": 0,
  "cost_yuan": 0.000558,
  "model": "deepseek-flash",
  "created_at": "2026-10-12T11:44:02+08:00"
}
```

**关键设计：只存 `chunk_ids`，不存切片正文。** 命中时从数据库按 id 重新取切片来重建引用。

- 好处：缓存条目小（省内存）；引用内容始终是最新的
- 必须处理：**按 id 取不到切片时（说明已被删除），视为缓存未命中**，绝不能返回残缺引用

### 4.5 键名规范

```
kb:v1:answer:{sha256前32位}          # 答案缓存，TTL 86400
kb:v1:rl:user:{owner_id}:{分钟窗口}   # L1 滑动窗口，ZSET，TTL 窗口长度
kb:v1:quota:user:{owner_id}:{日期}    # L3 每日配额，TTL 到次日零点
kb:v1:conc:llm                       # L2 全局并发计数，TTL 安全兜底
```

**为什么带 `v1`**：将来缓存结构变了（比如阶段 4 换成向量缓存），改个前缀就能让全部旧缓存自然失效，不用逐个删。

**为什么 `{日期}` 用"到次日零点的秒数"而不是固定 86400**：

```python
def seconds_until_midnight() -> int:
    now = datetime.now(CST)
    tomorrow = (now + timedelta(days=1)).replace(hour=0, minute=0, second=0, microsecond=0)
    return max(int((tomorrow - now).total_seconds()), 1)
```

用固定 86400 会导致配额窗口"漂移"——今天下午 3 点设的 key，明天下午 3 点才过期，用户会发现"配额不是按自然日重置的"。这个细节很多人做错。

## 5. 缓存实现

### 5.1 缓存抽象层（`app/clients/cache.py`）

**为什么要有抽象层**：测试用 fakeredis 注入，生产用真 Redis；两者接口一致。同时把「Redis 故障降级」的逻辑收在一个地方。

```python
"""Redis 客户端与缓存抽象。

设计要点：
1. 所有 Redis 操作都包 try/except —— Redis 故障绝不能导致问答接口 500。
2. 提供 Cache 协议，测试可注入 fakeredis 实现。
3. 缓存值存 JSON 字符串（不用 Hash），读写都是整体操作。
"""

import json
import logging
from datetime import datetime, timedelta
from typing import Any, Protocol
from zoneinfo import ZoneInfo

import redis.asyncio as aioredis
from redis.exceptions import RedisError

from app.core.config import settings

logger = logging.getLogger(__name__)

CST = ZoneInfo("Asia/Shanghai")


def seconds_until_midnight() -> int:
    """到次日零点的秒数。用于每日配额键的 TTL（不能用固定 86400，会漂移）。"""
    now = datetime.now(CST)
    tomorrow = (now + timedelta(days=1)).replace(
        hour=0, minute=0, second=0, microsecond=0
    )
    return max(int((tomorrow - now).total_seconds()), 1)


class CacheBackend(Protocol):
    """缓存后端协议：Redis 与 fakeredis 都满足它。"""

    async def get_json(self, key: str) -> dict[str, Any] | None: ...
    async def set_json(self, key: str, value: dict[str, Any], ttl: int) -> None: ...
    async def delete(self, key: str) -> None: ...


class RedisCache:
    """生产实现：redis-py 异步客户端。"""

    def __init__(self, client: aioredis.Redis) -> None:
        self._redis = client

    async def get_json(self, key: str) -> dict[str, Any] | None:
        try:
            raw = await self._redis.get(key)
        except RedisError as exc:
            logger.warning("缓存读取失败（降级为未命中）key=%s err=%s", key, exc)
            return None
        if raw is None:
            return None
        try:
            data = json.loads(raw)
        except json.JSONDecodeError:
            logger.warning("缓存内容损坏，删除该键 key=%s", key)
            await self.delete(key)
            return None
        return data if isinstance(data, dict) else None

    async def set_json(self, key: str, value: dict[str, Any], ttl: int) -> None:
        try:
            await self._redis.set(key, json.dumps(value, ensure_ascii=False), ex=ttl)
        except RedisError as exc:
            # 写缓存失败不影响本次回答，只记日志
            logger.warning("缓存写入失败 key=%s err=%s", key, exc)

    async def delete(self, key: str) -> None:
        try:
            await self._redis.delete(key)
        except RedisError as exc:
            logger.warning("缓存删除失败 key=%s err=%s", key, exc)


class MemoryCache:
    """纯内存实现：只在 redis_enabled=false 或单测时使用。

    ⚠️ 不是生产方案：多 worker 下每个进程一份，命中率被 worker 数量摊薄。
    """

    def __init__(self) -> None:
        self._store: dict[str, tuple[float, str]] = {}

    async def get_json(self, key: str) -> dict[str, Any] | None:
        import time

        item = self._store.get(key)
        if item is None:
            return None
        expire_at, raw = item
        if expire_at < time.time():
            self._store.pop(key, None)
            return None
        return json.loads(raw)

    async def set_json(self, key: str, value: dict[str, Any], ttl: int) -> None:
        import time

        self._store[key] = (time.time() + ttl, json.dumps(value, ensure_ascii=False))

    async def delete(self, key: str) -> None:
        self._store.pop(key, None)


_redis_client: aioredis.Redis | None = None
_cache: CacheBackend | None = None


async def startup_cache() -> CacheBackend:
    """在 lifespan 里调用。Redis 连不上时自动降级为内存缓存，服务照常可用。"""
    global _redis_client, _cache

    if not settings.redis_enabled:
        logger.warning("REDIS_ENABLED=false，使用进程内内存缓存（生产不可用）")
        _cache = MemoryCache()
        return _cache

    _redis_client = aioredis.from_url(
        settings.redis_url,
        encoding="utf-8",
        decode_responses=True,
        socket_timeout=settings.redis_socket_timeout,   # 必须设！否则 Redis 卡住会拖垮接口
        socket_connect_timeout=settings.redis_socket_timeout,
        health_check_interval=30,
    )
    try:
        await _redis_client.ping()
        logger.info("Redis 已连接: %s", settings.redis_url)
        _cache = RedisCache(_redis_client)
    except RedisError as exc:
        logger.error("Redis 连接失败，降级为内存缓存: %s", exc)
        _cache = MemoryCache()

    return _cache


async def shutdown_cache() -> None:
    global _redis_client, _cache
    if _redis_client is not None:
        await _redis_client.aclose()
        _redis_client = None
    _cache = None


def get_cache() -> CacheBackend:
    """FastAPI 依赖；测试里用 dependency_overrides 换成 fakeredis 版本。"""
    if _cache is None:
        raise RuntimeError("缓存未初始化：请在 lifespan 中 await startup_cache()")
    return _cache


def get_redis() -> aioredis.Redis:
    """给限流模块用（需要 ZSET / Lua 等原生命令，超出 Cache 协议范围）。"""
    if _redis_client is None:
        raise RuntimeError("Redis 未初始化或已降级为内存缓存")
    return _redis_client
```

### 5.3 缓存键构造（`app/services/cache_key.py`）

单独成文件，因为**它必须被测试覆盖**（键算错的后果是返回错答案或泄露数据）。

```python
"""缓存键构造。正确性关键：必须包含 owner_id，防止跨用户泄露。"""

import hashlib
import re

from app.core.config import settings
from app.services.retrieval import RetrievedChunk


def normalize_question(question: str) -> str:
    """归一化：去首尾空白、压缩内部空白、转小写、去掉结尾标点。

    目的：让"退款要多久？" 和 "退款要多久" 命中同一条缓存。
    ⚠️ 不要做更激进的归一化（如去停用词、同义词替换），那是语义缓存的活，
      在阶段 1 做会带来"看起来相同其实想问的不一样"的风险。
    """
    q = question.strip()
    q = re.sub(r"\s+", " ", q)
    q = q.lower()
    q = re.sub(r"[？?！!。.，,、；;：:]+$", "", q)
    return q


def context_fingerprint(chunks: list[RetrievedChunk]) -> str:
    """本次检索结果的指纹：切片 id + 内容哈希。

    内容哈希而非只用 id：文档被更新（同 id 内容变了）时指纹必须变。
    """
    h = hashlib.sha256()
    for c in chunks:
        h.update(f"{c.chunk_id}:".encode())
        h.update(hashlib.sha256(c.content.encode("utf-8")).hexdigest().encode())
        h.update(b"|")
    return h.hexdigest()


def answer_cache_key(*, owner_id: int, question: str, chunks: list[RetrievedChunk]) -> str:
    """★ 缓存键 = owner_id + 归一化问题 + 检索结果指纹。

    为什么必须含 owner_id：否则 A 用户的问题命中 B 用户的答案 = 数据泄露。
    """
    raw = f"{owner_id}|{normalize_question(question)}|{context_fingerprint(chunks)}"
    digest = hashlib.sha256(raw.encode("utf-8")).hexdigest()[:32]
    return f"{settings.cache_key_prefix}:v1:answer:{digest}"
```

### 5.4 `qa.py` 的改造

只剩两个关键改动：**查缓存 → 命中则跳过 LLM → 未命中则查完写缓存**。

```python
"""拼 prompt → 调 LLM → 组装引用。阶段 1：加入答案缓存。

对应阶段 1 文档 §5.4。
"""

import logging

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.clients.llm import LLMClient
from app.core.config import settings
from app.models.chat_log import ChatLog
from app.models.chunk import Chunk
from app.services.cache_key import answer_cache_key
from app.services.ratelimit import distributed_llm_slot
from app.services.retrieval import RetrievedChunk, search

logger = logging.getLogger(__name__)

SYSTEM_PROMPT = """你是一个严谨的知识库问答助手。请遵守以下规则：

1. 只根据【参考资料】回答，不要使用你自己的知识补充事实。
2. 如果参考资料不足以回答，直接回答"根据现有资料无法回答"，不要编造。
3. 回答简洁准确，不要复述问题，不要输出与问题无关的内容。
4. 在引用具体内容时，用 [1] [2] 的形式标注来源编号。
"""


def build_context(chunks: list[RetrievedChunk], max_chars: int | None = None) -> str:
    max_chars = max_chars or settings.max_context_chars
    parts: list[str] = []
    used = 0
    for i, c in enumerate(chunks, start=1):
        block = f"[{i}] 来源：《{c.document_title}》第 {c.seq + 1} 段\n{c.content}"
        if used + len(block) > max_chars:
            break
        parts.append(block)
        used += len(block)
    return "\n\n".join(parts)


async def _hydrate_citations(
    db: AsyncSession, chunk_ids: list[int]
) -> list[RetrievedChunk] | None:
    """按 id 重建引用。任一 id 取不到（文档已被删）→ 返回 None，调用方视为未命中。

    绝不能"尽力而为"地返回残缺引用——那会让用户看到一个指向不存在文档的答案。
    """
    if not chunk_ids:
        return None
    stmt = select(Chunk).where(Chunk.id.in_(chunk_ids))
    rows = {c.id: c for c in (await db.scalars(stmt)).all()}
    if len(rows) != len(set(chunk_ids)):
        return None
    result: list[RetrievedChunk] = []
    for cid in chunk_ids:
        c = rows[cid]
        result.append(
            RetrievedChunk(
                chunk_id=c.id,
                document_id=c.document_id,
                document_title="",      # 由调用方补；此处不额外 join 文档表
                seq=c.seq,
                content=c.content,
                score=0.0,
            )
        )
    return result


async def answer(
    db: AsyncSession,
    llm: LLMClient,
    cache,
    *,
    owner_id: int,
    question: str,
    top_k: int | None = None,
) -> tuple[str, list[RetrievedChunk], dict]:
    chunks = await search(db, owner_id=owner_id, question=question, top_k=top_k)

    if not chunks:
        # 没检索到内容 → 不调 LLM、也不写缓存（这种回答不值得缓存）
        return (
            "知识库中没有找到与该问题相关的内容。请先上传相关文档，或换一种问法。",
            [],
            {
                "prompt_tokens": 0, "completion_tokens": 0,
                "cost_yuan": 0.0, "latency_ms": 0,
                "cache_hit": False, "retrieval_mode": "keyword",
            },
        )

    cache_key = answer_cache_key(owner_id=owner_id, question=question, chunks=chunks)

    # ---------- 1. 查缓存 ----------
    if settings.cache_enabled:
        cached = await cache.get_json(cache_key)
        if cached is not None:
            citations = await _hydrate_citations(db, cached.get("chunk_ids", []))
            if citations is not None:
                logger.info(
                    '{"event":"chat","user":%s,"cache_hit":true,"saved_cost_yuan":%s}',
                    owner_id, cached.get("cost_yuan", 0.0),
                )
                db.add(
                    ChatLog(
                        owner_id=owner_id, question=question,
                        answer=cached.get("answer", ""),
                        prompt_tokens=0, completion_tokens=0, cached_tokens=0,
                        cost_yuan=0.0,                    # 本次真实花费为 0
                        latency_ms=0,
                        model=cached.get("model", ""),
                        is_off_peak=False,
                        cited_chunk_ids=[c.chunk_id for c in citations],
                        cache_hit=True,
                    )
                )
                return (
                    cached.get("answer", ""),
                    citations,
                    {
                        "prompt_tokens": 0, "completion_tokens": 0,
                        "cost_yuan": 0.0,
                        "latency_ms": 0,
                        "cache_hit": True,
                        "saved_cost_yuan": cached.get("cost_yuan", 0.0),
                        "retrieval_mode": "keyword",
                    },
                )
            # 引用失效 → 落到正常生成路径（不删旧键，靠 TTL 自然过期）
            logger.info('{"event":"cache_stale","user":%s}', owner_id)

    # ---------- 2. 未命中：调 LLM（带分布式并发控制）----------
    context = build_context(chunks)
    user_prompt = f"""【参考资料】
{context}

【问题】
{question}

请根据参考资料回答，并标注引用编号。"""

    async with distributed_llm_slot():
        result = await llm.chat(
            [
                {"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": user_prompt},
            ],
            temperature=0.2,
            user_id=f"u{owner_id}",
        )

    # ---------- 3. 写缓存 ----------
    if settings.cache_enabled and result.content.strip():
        await cache.set_json(
            cache_key,
            {
                "answer": result.content,
                "chunk_ids": [c.chunk_id for c in chunks],
                "prompt_tokens": result.prompt_tokens,
                "completion_tokens": result.completion_tokens,
                "cached_tokens": result.cached_tokens,
                "cost_yuan": result.cost_yuan,
                "model": result.model,
            },
            ttl=settings.cache_ttl_seconds,
        )

    db.add(
        ChatLog(
            owner_id=owner_id, question=question, answer=result.content,
            prompt_tokens=result.prompt_tokens,
            completion_tokens=result.completion_tokens,
            cached_tokens=result.cached_tokens,
            cost_yuan=result.cost_yuan,
            latency_ms=result.latency_ms,
            model=result.model,
            is_off_peak=not result.peak,
            cited_chunk_ids=[c.chunk_id for c in chunks],
            cache_hit=False,
        )
    )

    logger.info(
        '{"event":"chat","user":%s,"cache_hit":false,"retrieved":%s,'
        '"prompt_tokens":%s,"completion_tokens":%s,"cached_tokens":%s,'
        '"cost_yuan":%s,"latency_ms":%s}',
        owner_id, len(chunks), result.prompt_tokens, result.completion_tokens,
        result.cached_tokens, result.cost_yuan, result.latency_ms,
    )

    return (
        result.content,
        chunks,
        {
            "prompt_tokens": result.prompt_tokens,
            "completion_tokens": result.completion_tokens,
            "cost_yuan": result.cost_yuan,
            "latency_ms": result.latency_ms,
            "cache_hit": False,
            "retrieval_mode": "keyword",
        },
    )
```

> **`_hydrate_citations` 里的 `document_title` 留空**：为省一次 join，标题由端点层从 chunks 关联的文档补。实现时你可以在 `_hydrate_citations` 里加一次 `join(Document)`——两种都行，**但不要在缓存里存标题**（文档改名后缓存就过期了）。

## 6. 多级限流

### 6.1 为什么需要三级，而不是一个

| 级别 | 防什么 | 算法 | 键 |
| --- | --- | --- | --- |
| **L1 频率** | 手速/脚本刷接口 | 滑动窗口（ZSET） | `rl:user:{id}` |
| **L2 并发** | 打满上游 + 打满自己的协程 | Redis 计数信号量（Lua） | `conc:llm` |
| **L3 配额** | 一天烧掉一个月预算 | 固定窗口计数（按自然日） | `quota:user:{id}:{date}` |

阶段 0 的 `asyncio.Semaphore(10)` 只在单进程有效，**多 worker 时实际并发是 10 × worker 数**——这就是 L2 必须上 Redis 的原因。

### 6.2 实现（`app/services/ratelimit.py`）

```python
"""多级限流：L1 频率 / L2 并发 / L3 每日配额。

Redis 故障策略由 RATELIMIT_FAIL_OPEN 控制：
  true （默认）= 放行。可用性优先。本项目是学习/内部工具，宁可多花钱也别让服务不可用。
  false        = 拒绝。成本优先。对外收费的产品应该这样。
⚠️ 这是产品决策，不是技术决策，部署到真实环境前必须明确选一个。
"""

import logging
import time
import uuid
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager
from datetime import datetime

from fastapi import HTTPException, status

from app.clients.cache import CST, get_redis, seconds_until_midnight
from app.core.config import settings

logger = logging.getLogger(__name__)

# L1 滑动窗口：清理过期 + 加入本次 + 计数 + 续期，四步在 pipeline 里一次往返
_SLIDING_WINDOW_LUA = """
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local member = ARGV[4]

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
redis.call('ZADD', key, now, member)
local count = redis.call('ZCARD', key)
redis.call('EXPIRE', key, window)
if count > limit then
  -- 超限：把自己刚加的那条撤回，避免"被拒绝的请求也占额度"
  redis.call('ZREM', key, member)
  return count - 1
end
return count
"""

# L2 并发信号量：只在 count <= max 时占用
_ACQUIRE_LUA = """
local key = KEYS[1]
local max = tonumber(ARGV[1])
local ttl = tonumber(ARGV[2])
local cur = tonumber(redis.call('GET', key) or '0')
if cur >= max then
  return 0
end
redis.call('INCR', key)
redis.call('EXPIRE', key, ttl)
return 1
"""

# L2 释放：只在 key 存在且 > 0 时 DECR，避免"过期后 DECR 变负数"导致永久占位
_RELEASE_LUA = """
local key = KEYS[1]
local cur = tonumber(redis.call('GET', key) or '0')
if cur > 0 then
  redis.call('DECR', key)
  return cur - 1
end
return 0
"""


def _fail_open() -> bool:
    return settings.ratelimit_fail_open


async def check_rate_limit(owner_id: int) -> None:
    """L1：每用户每分钟请求数。超限抛 429。"""
    if not settings.redis_enabled:
        return
    try:
        redis = get_redis()
        now = time.time()
        member = f"{now:.6f}-{uuid.uuid4().hex[:8]}"
        count = await redis.eval(
            _SLIDING_WINDOW_LUA,
            1,
            f"{settings.cache_key_prefix}:v1:rl:user:{owner_id}",
            now,
            settings.rate_limit_per_minute * 60 // max(settings.rate_limit_per_minute, 1)
            if False else 60,                      # 窗口固定 60 秒，见下方说明
            settings.rate_limit_per_minute,
            member,
        )
        if int(count) > settings.rate_limit_per_minute:
            raise HTTPException(
                status_code=status.HTTP_429_TOO_MANY_REQUESTS,
                detail={
                    "code": 42901,
                    "message": f"请求过于频繁，每分钟最多 {settings.rate_limit_per_minute} 次",
                    "detail": None,
                },
                headers={"Retry-After": "60"},
            )
    except HTTPException:
        raise
    except Exception as exc:                        # noqa: BLE001 - Redis 故障不能影响主流程
        logger.warning("L1 限流检查失败: %s", exc)
        if not _fail_open():
            raise HTTPException(
                status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
                detail={"code": 50302, "message": "限流服务不可用，请稍后重试", "detail": None},
            ) from exc


async def check_daily_quota(owner_id: int) -> None:
    """L3：每用户每日 LLM 调用次数。**只在缓存未命中、即将真正调 LLM 时调用**。"""
    if not settings.redis_enabled:
        return
    try:
        redis = get_redis()
        today = datetime.now(CST).strftime("%Y%m%d")
        key = f"{settings.cache_key_prefix}:v1:quota:user:{owner_id}:{today}"
        used = await redis.incr(key)
        if used == 1:
            await redis.expire(key, seconds_until_midnight())
        if used > settings.daily_llm_quota:
            raise HTTPException(
                status_code=status.HTTP_429_TOO_MANY_REQUESTS,
                detail={
                    "code": 42902,
                    "message": f"今日 AI 调用额度已用完（{settings.daily_llm_quota} 次），明日重置",
                    "detail": None,
                },
            )
    except HTTPException:
        raise
    except Exception as exc:                        # noqa: BLE001
        logger.warning("L3 配额检查失败: %s", exc)
        if not _fail_open():
            raise


@asynccontextmanager
async def distributed_llm_slot() -> AsyncIterator[None]:
    """L2：全局并发槽位。替代阶段 0 的进程内 asyncio.Semaphore。

    用轮询等待而不是阻塞队列——实现简单、不会死锁。
    并发上限 10 时，第 11 个请求最多等约 0.3s，完全可接受。
    """
    if not settings.redis_enabled:
        yield
        return

    key = f"{settings.cache_key_prefix}:v1:conc:llm"
    acquired = False
    deadline = time.monotonic() + 10.0            # 最多等 10 秒

    try:
        while time.monotonic() < deadline:
            try:
                ok = await get_redis().eval(
                    _ACQUIRE_LUA,
                    1,
                    key,
                    settings.llm_max_concurrency,
                    30,               # 安全 TTL：进程崩溃时槽位 30 秒后自动释放
                )
            except Exception as exc:                  # noqa: BLE001
                logger.warning("L2 并发控制失败（放行）: %s", exc)
                yield
                return
            if int(ok) == 1:
                acquired = True
                break
            await _async_sleep(0.1)

        if not acquired:
            raise HTTPException(
                status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
                detail={"code": 50303, "message": "AI 服务繁忙，请稍后重试", "detail": None},
            )

        yield
    finally:
        if acquired:
            try:
                await get_redis().eval(_RELEASE_LUA, 1, key)
            except Exception as exc:                  # noqa: BLE001
                logger.warning("L2 释放槽位失败（靠 TTL 兜底）: %s", exc)


async def _async_sleep(seconds: float) -> None:
    import asyncio

    await asyncio.sleep(seconds)
```

> **那段 L1 的窗口参数写得很难看**（我留了个 `if False else 60` 的痕迹），实现时请直接写成 `60`，并把窗口长度做成配置项 `rate_limit_window_seconds: int = 60`。这里保留原样是想让你看到"参数从配置推导"时容易写歪，别照抄。

### 6.3 三个必须注意的点

1. **L3 配额只能在"即将真正调用 LLM"时扣减**，不能在请求入口就扣。否则缓存命中的请求也会吃掉配额——**那等于把缓存省下来的钱又扣掉了**，逻辑上自相矛盾。
2. **L1 的滑动窗口要撤回被拒绝的那条记录**（Lua 里已处理）。否则用户被限流期间每重试一次就多占一个坑位，**导致限流时间被无限延长**——这是滑动窗口实现最常见的 bug。
3. **L2 的释放必须防负数**。如果 `ACQUIRE` 后进程崩了、key 在 TTL 后过期，随后 `finally` 里的 `DECR` 会把计数变成 -1，等于**永久多出一个槽位**（累积几次就绕过了并发限制）。用 Lua 判断 `cur > 0` 再减。

## 8. 端点层改动

`POST /api/v1/chat` 的响应新增两个字段，**不要在端点里做限流**（限流在 service 层，因为 L3 要等缓存判断之后）：

```python
# app/api/v1/endpoints/chat.py
@router.post("", response_model=ChatResponse)
async def chat(
    payload: ChatRequest,
    db: DBSession,
    llm: LLMDep,
    cache: CacheDep,
    user: CurrentUser,
) -> ChatResponse:
    await check_rate_limit(user.id)          # L1：最早拦，最省资源

    answer_text, chunks, usage = await answer(
        db, llm, cache, owner_id=user.id, question=payload.question, top_k=payload.top_k
    )
    return ChatResponse(
        answer=answer_text,
        citations=[...],
        usage=usage,
        retrieval_mode=usage.get("retrieval_mode", "keyword"),
        cache_hit=usage.get("cache_hit", False),          # ← 新增
        saved_cost_yuan=usage.get("saved_cost_yuan"),     # ← 新增，仅命中时有值
    )
```

`CacheDep` 在 `deps.py` 里定义：

```python
from app.clients.cache import CacheBackend, get_cache

CacheDep = Annotated[CacheBackend, Depends(get_cache)]
```

**为什么把 `cache` 作为依赖注入而不是全局调用**：测试里用 `app.dependency_overrides[get_cache]` 注入 fakeredis，**测试之间互不干扰**（每个测试一个独立的假 Redis 实例）。如果 service 里直接 `from ... import get_cache` 调用全局单例，测试会互相污染缓存。

## 9. 可观测性

### 9.1 新增的结构化日志字段

```json
{"event":"chat","user":1,"cache_hit":true,"saved_cost_yuan":0.000558}
{"event":"chat","user":1,"cache_hit":false,"retrieved":1,"prompt_tokens":199,
 "completion_tokens":20,"cached_tokens":0,"cost_yuan":0.000558,"latency_ms":869}
```

### 9.2 阶段 1 结束必须能回答的四个问题

```sql
-- 1. 缓存命中率（最核心的指标）
SELECT
  count(*) FILTER (WHERE cache_hit) AS 命中次数,
  count(*) AS 总次数,
  round(100.0 * count(*) FILTER (WHERE cache_hit) / nullif(count(*), 0), 1) AS 命中率百分比
FROM chat_logs;

-- 2. 缓存省下的钱（注意：命中时 cost_yuan 记 0，所以省下的钱要从别处算）
--    → 用"未命中时的平均成本 × 命中次数"估算
SELECT
  round(avg(cost_yuan) FILTER (WHERE NOT cache_hit)::numeric, 6) AS 平均单次成本,
  count(*) FILTER (WHERE cache_hit) AS 命中次数
FROM chat_logs;

-- 3. 命中 vs 未命中的延迟差（证明缓存的价值）
SELECT cache_hit, round(avg(latency_ms)) AS 平均延迟, count(*)
FROM chat_logs GROUP BY cache_hit;

-- 4. 每个用户的用量与花费（验证多用户隔离 + 配额是否生效）
SELECT owner_id, count(*) AS 次数,
       round(sum(cost_yuan)::numeric, 4) AS 花费,
       count(*) FILTER (WHERE cache_hit) AS 命中
FROM chat_logs GROUP BY owner_id ORDER BY 花费 DESC;
```

> **第 2 条要特别注意**：命中时我把 `cost_yuan` 记成 0（真实花费），所以"省下的钱"不能直接 SUM。要么按上面的估算，要么额外加一列 `saved_cost_yuan`。**推荐后者**——数据是给未来的你看的，别让它需要"估算"才能读懂。加列的话把它和 `cache_hit` 一起加，一次迁移搞定。

```python
    # ...
```

> ⚠️ `ratelimit.get_redis()` 和 `cache.get_cache()` 是两条不同的获取路径（前者为了用 ZSET/Lua 原生命令）。测试里**两条都要打桩**，否则一跑限流就会去连真实的 localhost:6379 然后失败或超时。这个坑很隐蔽——**建议给 `ratelimit` 也改成依赖注入**，那样只需 override 一处。我在文档里保留现状是为了让你看清这个设计缺陷，实现时请统一成依赖注入。

### 10.2 必须覆盖的测试

| 测试文件 | 用例 | 断言要点 |
| --- | --- | --- |
| `test_cache_key.py` | 相同问题不同写法 | "退款要多久？" 与 "退款要多久" 归一化后**同键** |
| | **不同用户同问题** | **必须是不同的键**（防泄露，最关键的断言） |
| | 相同问题但 chunks 不同 | 键不同 |
| | chunks 内容变了（同 id） | 键不同 |
| `test_cache.py` | 写→读 | 能取回原值 |
| | 过期 | 过期后取不到（可用 fakeredis 的时间控制或直接传 ttl=0） |
| | 存了非 JSON 内容 | `get_json` 返回 None 且**不抛异常** |
| | Redis 抛异常时 | `get_json` 返回 None（降级为未命中），**不冒泡** |
| `test_chat_cache.py` | **同问题问两次** | 第二次 `fake_llm.calls` **不再增加**（核心收益） |
| | 第二次响应 | `cache_hit=true`，`cost_yuan=0` |
| | **上传新文档后再问同问题** | 缓存未命中（`fake_llm.calls` 增加） |
| | **删除被引用文档后再问** | 不返回失效引用（要么未命中，要么引用正确） |
| | `CACHE_ENABLED=false` | 每次都调 LLM |
| `test_ratelimit.py` | L1 超过 N 次 | 第 N+1 次返回 429 + `Retry-After` |
| | L1 被拒后 | **不占用额度**（重试不会延长限流） |
| | L3 配额用尽 | 返回 42902 + "额度已用完" |
| | **缓存命中时** | **不扣 L3 配额**（关键：否则缓存白做） |
| | L2 并发 | 超过上限时排队或 503，不会无限并发 |
| | L2 进程崩溃模拟 | key 过期后 DECR **不会变负数** |
| | Redis 全部失败 + fail_open=true | 请求**照常成功** |
| | Redis 全部失败 + fail_open=false | 返回 503 |

**其中三条是"防回归的关键断言"，请务必写**：
1. **不同用户同问题 → 键不同**（这是安全事故的防线）
2. **上传文档后同问题 → 缓存失效**（这是"改了文档答案不变"bug 的防线）
3. **缓存命中不扣配额**（这是逻辑自洽的防线）

## 12. 风险与已知取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 命中率可能很低 | 个人知识库的问题往往各不相同，"完全相同的问题"未必多 | **先测基线再优化**。别急着上语义缓存，先看数据 |
| 缓存命中仍需检索 | 省了 LLM 但没省 SQL | 阶段 1 可接受（15ms vs 800ms）；阶段 4 检索变慢后再考虑两级缓存 |
| Redis 成为单点 | Redis 挂了 → 缓存失效 + 限流失效 | `fail_open=true` 保证可用性；Redis 本身要配持久化和主从（离开本项目范围） |
| 内存缓存降级后命中率骤降 | 多 worker 各一份 | 只在开发期接受；生产必须让 Redis 可用并**在监控里对降级告警** |
| 配额按自然日重置 | 用户可能卡在 23:59 用光 | 可接受；要更平滑可改滚动 24 小时窗口 |
| `cache_hit` 加了列 | 用 `create_all` 不会自动加列 | 删库重建，或**本阶段引入 Alembic**（推荐） |

## 13. 升级钩子（阶段 2 改哪里）

| 阶段 2 要做的 | 改哪里 | 是否动本阶段成果 |
| --- | --- | --- |
| 流式 SSE | `llm.py` 加 `chat_stream()`；新增 `/chat/stream` | 缓存逻辑要重写：**流式响应无法先查缓存再返回**，需改用"边流边攒，结束后写缓存" |
| 会话记忆 | 新增 `chat_sessions` / `chat_messages` 表 | 缓存键要**加入会话上下文指纹**，否则多轮对话会互相命中（**这是个真陷阱，阶段 1 的单轮假设到此为止**） |
| 极限并发优化 | `ratelimit.py` 的轮询改为阻塞列表 | 不改接口 |

> **提前预警阶段 2 的最大陷阱**：多轮对话引入后，`(问题 + 检索指纹)` 不再足以定位答案——同一句"那要多久？"在不同会话上下文里含义完全不同。**必须把会话历史的指纹也纳入缓存键**，否则会出现"追问命中了上一个会话的答案"。这个坑在阶段 2 文档里会展开。
