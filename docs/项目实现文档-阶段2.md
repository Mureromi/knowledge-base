## 1. ★ 四个实测结论（写代码前必须先知道）

我在你的环境里实测了 DeepSeek 的流式接口，四个结论都会直接影响实现，其中两个和"网上教程的写法"不一样。

### 1.1 ★ 流式响应**默认就返回 usage**，不需要 `stream_options`

OpenAI 的流式接口默认不返回 token 用量，必须显式传 `stream_options: {"include_usage": true}`。**DeepSeek 不需要**：

```
=== 不带 stream_options ===
  usage 块: {"prompt_tokens": 12, "completion_tokens": 24,
            "prompt_cache_hit_tokens": 0, "prompt_cache_miss_tokens": 12}
=== 带 stream_options={'include_usage': True} ===
  usage 块: {"prompt_tokens": 12, "completion_tokens": 24, ...}   ← 完全一样
```

**这很重要**：意味着阶段 0/1 建立的成本统计能力在流式下**不会断**。如果按 OpenAI 的习惯去写、以为不传就拿不到 usage，你会白写一堆估算逻辑。

### 1.2 结束标记是 `data: [DONE]`

标准的 OpenAI 风格终止符，必须显式判断，否则 `json.loads("[DONE]")` 会抛异常。

### 1.3 keep-alive 是注释行，实测没出现但必须防

我这次实测 **keep-alive 注释行 = 0**（因为本地到服务端很快，模型没进入长时间等待）。但阶段 0 文档已记录：**等待推理时 DeepSeek 会持续返回 SSE 注释（`: keep-alive`）**。所以解析器**必须过滤**：

```python
if not line.strip() or line.startswith(":"):
    continue
```

**别因为自己测的时候没出现就跳过这一步**——一旦线上模型排队，注释行就会来，而 `line[5:]` 去解析一个 `: keep-alive` 会直接崩。

### 1.4 ★ 开启思考模式时，`delta` 里有 `reasoning_content` 和 `content` 两个字段

为了确认边界行为，我又测了一次 `thinking=enabled` 的流式：

```
delta 中出现过的字段: {'role': 1, 'content': 222, 'reasoning_content': 222}
reasoning_content 累计: 215 字
content 累计:           112 字 -> '如果按**普通数字**比较：  \n**9.8 更大**...'
usage: completion=221 reasoning=148
```

**两个后果**：

1. **思维链是逐块流出来的**，和正文交错在不同 chunk 里。
2. **如果把 `reasoning_content` 也当正文流式推给用户，用户会看到模型的内心独白。** 必须以不同的 SSE 事件类型区分（见 §5.3）。

好消息：你的配置 `LLM_THINKING=false`，阶段 2 默认走非思考路径，`delta` 里只有 `content`。**但解析器仍要显式忽略 `reasoning_content`**，否则哪天你打开思考模式，用户界面会立刻"漏出思维链"。

### 2.2 为什么拆成两张表而不是一张

`chat_messages` 只存消息本身，`chat_sessions` 存会话元信息。好处：

- 列出"我的会话列表"时**不需要扫全部消息**（`ORDER BY last_active_at DESC` 直接走索引）
- 会话级操作（重命名、删除、置顶）不用碰消息表
- 将来做"会话分享"只需在 session 上加一个字段

### 2.3 `chat_logs` 增加会话溯源

用 `SET NULL` 而不是 `CASCADE`：**会话被删掉时，成本记录不能跟着消失**——那是你要用来做长期成本分析的数据。这是"审计数据"和"业务数据"生命周期不同的典型场景。

## 3. 会话与滑动窗口

### 3.1 滑动窗口的定义（**这个定义要和缓存键严格一致**）

```python
# app/services/session.py
"""会话历史管理。滑动窗口 + 缓存键指纹，两者必须用同一个窗口函数。"""

import logging

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.config import settings
from app.models.chat_message import ChatMessage
from app.models.chat_session import ChatSession

logger = logging.getLogger(__name__)


async def get_or_create_session(
    db: AsyncSession, *, owner_id: int, session_id: int | None, first_question: str
) -> ChatSession:
    """取会话；session_id 为 None 则新建。越权检查在这里做。"""
    if session_id is not None:
        stmt = select(ChatSession).where(
            ChatSession.id == session_id,
            ChatSession.owner_id == owner_id,      # ★ 越权检查：绝不允许访问他人会话
        )
        session = (await db.scalars(stmt)).one_or_none()
        if session is None:
            # 不区分"不存在"和"不属于你"，避免探测他人会话 id 是否存在
            from fastapi import HTTPException, status as http_status

            raise HTTPException(
                status_code=http_status.HTTP_404_NOT_FOUND,
                detail={"code": 40402, "message": "会话不存在", "detail": None},
            )
        return session

    session = ChatSession(
        owner_id=owner_id,
        title=first_question.strip()[:200],
    )
    db.add(session)
    await db.flush()
    await db.refresh(session)
    return session


async def load_window_messages(
    db: AsyncSession, *, session_id: int, limit_turns: int | None = None
) -> list[dict[str, str]]:
    """★ 加载最近 N 轮历史，转成 LLM messages 格式。

    返回的顺序是"从旧到新"，直接可拼进 messages 数组。

    为什么按"轮"而不是"条"取：一轮 = 一次 user + 一次 assistant。
    只取最近 2N 条消息，才能保证不会出现"有 assistant 回答但缺 user 提问"的错位。
    """
    turns = limit_turns or settings.session_window_turns
    max_messages = turns * 2

    stmt = (
        select(ChatMessage)
        .where(ChatMessage.session_id == session_id)
        .order_by(ChatMessage.id.desc())
        .limit(max_messages)
    )
    rows = list((await db.scalars(stmt)).all())
    rows.reverse()          # 倒序取、正序用
    return [{"role": m.role, "content": m.content} for m in rows]


def history_fingerprint(window_messages: list[dict[str, str]]) -> str:
    """★ 窗口内历史的指纹，用于缓存键。

    必须用"窗口内的消息"而不是"整个会话的历史"：
    因为真正影响 LLM 输出的就是窗口内的内容（见 §4.1）。
    """
    import hashlib

    h = hashlib.sha256()
    for m in window_messages:
        h.update(m["role"].encode())
        h.update(b"\x00")
        h.update(m["content"].encode("utf-8"))
        h.update(b"\x01")
    return h.hexdigest()
```

### 3.2 ★ 写入顺序的坑：缓存键必须在"写入本轮消息"之前算

这是个很容易写错、且**不会报错只会静默失效**的地方：

```
❌ 错误顺序：
   1. 把本轮 user 消息写库
   2. 读最近 6 轮历史 → 这里已经把本轮问题包含进去了
   3. 算缓存键
   → 结果：每一轮的"历史指纹"都不一样（因为历史里多了本轮问题），
     缓存永远不可能命中。

✅ 正确顺序：
   1. 读窗口历史（此时不含本轮）
   2. 算缓存键 = f(问题, 历史指纹, 检索指纹)
   3. 查缓存
   4. 无论命中与否，最后再写入本轮 user + assistant 消息
```

**文档里必须写死这个顺序**，并在测试里断言"连问两次完全相同的问题，第二次命中缓存"（`test_multiturn_cache.py`）——这条测试就是用来防这个顺序写错的。

### 3.3 会话的 `last_active_at` 维护

每次问答结束后更新：

```python
session.last_active_at = datetime.now(UTC)
```

用途：会话列表排序、"最近 7 天活跃会话"统计。**不要用 `created_at` 排序**，用户会找不到自己刚聊过的会话。

## 4. 缓存键的升级（阶段 2 最核心的设计）

### 4.1 从"问题 + 检索指纹"到"问题 + 历史指纹 + 检索指纹"

阶段 1 的键是：

```
key = sha256(f"{owner_id}|{归一化问题}|{检索指纹}")
```

它的**正确性依赖一个隐含前提：问题是自包含的**。阶段 2 打破了这个前提：

> 用户问「**那要多久？**」——单看这句话无法确定问的是什么，必须结合上一轮。

如果继续用阶段 1 的键，会出现**静默的错误答案**：用户在会话 A 里问过「退款要多久」，会话 B 里问「那要多久」（指退货），会命中会话 A 的答案。

升级后：

```python
key = sha256(f"{owner_id}|{归一化问题}|{历史指纹}|{检索指纹}")
```

### 4.2 ★ 为什么指纹必须用"窗口内的历史"，而不是"整个会话的历史"

如果指纹用**全部**历史，会出现一个反直觉的后果：**几乎永远不可能命中缓存**，因为每多聊一轮，指纹就变一次。

用**窗口内**历史（最近 6 轮）则语义自洽：

| 场景 | 窗口是否变化 | 结果 |
| --- | --- | --- |
| 在一个"已经聊了 20 轮、窗口稳定在最后 6 轮"的会话里，重复问刚才问过的问题 | 窗口**不变** | **命中缓存** ✅ |
| 会话刚开始，历史从 0 轮变成 1 轮 | 窗口变化 | 未命中（合理：上下文确实变了） |
| 同一个问题在两个不同会话里问 | 窗口不同 | 未命中（**这正是我们要的隔离**）✅ |

**关键洞察**：指纹要覆盖的是"**实际送进 LLM 的那部分上下文**"，不多不少。

- 多了（整会话历史）→ 缓存永远不命中，等于白做
- 少了（只用问题）→ 返回错误答案，比不做缓存更糟

**这是"缓存键必须精确匹配影响输出的所有输入"这条通用原则的具体体现**，也是阶段 2 最值得记住的一课。

### 4.3 缓存键实现

```python
# app/services/cache_key.py 改造
def answer_cache_key(
    *,
    owner_id: int,
    question: str,
    chunks: list[RetrievedChunk],
    window_messages: list[dict[str, str]] | None = None,
) -> str:
    """★ 缓存键 = owner_id + 归一化问题 + 窗口历史指纹 + 检索结果指纹。

    window_messages 必须与真正发给 LLM 的历史完全一致 —— 见文档 §4.2。
    """
    from app.services.session import history_fingerprint

    hist = history_fingerprint(window_messages or [])
    raw = f"{owner_id}|{normalize_question(question)}|{hist}|{context_fingerprint(chunks)}"
    digest = hashlib.sha256(raw.encode("utf-8")).hexdigest()[:32]
    # 版本号从 v1 升到 v2：键结构变了，旧缓存自然失效，不用手动清
    return f"{settings.cache_key_prefix}:v2:answer:{digest}"
```

> **为什么把 `v1` 升到 `v2` 而不是继续用 `v1`**：键结构变了，旧键永远不会被命中，留着只占内存。升版本号让 Redis 里的旧缓存自然过期，且**不需要写任何清理脚本**。这就是阶段 1 文档里"前缀带版本号"设计的兑现。

### 4.4 缓存里要存 `session_id` 吗

**不存**。因为同一个键可能被不同会话命中（两个会话的窗口恰好相同），存了会串会话。

命中时 `chat_logs.session_id` 用**当前请求的会话 id**，这是正确的：这次请求确实发生在这个会话里。

## 5. 流式实现

### 5.1 `LLMClient.chat_stream()`（`app/clients/llm.py` 新增）

```python
"""流式对话。与 chat() 并列，共享 payload 构造与 _parse 的字段解析。"""

import json
from collections.abc import AsyncIterator
from dataclasses import dataclass
from typing import Literal

import httpx

from app.clients.llm import LLMError, LLMResult, RETRYABLE_STATUS
from app.clients.pricing import calc_cost, is_peak_now
from app.core.config import settings


@dataclass
class StreamChunk:
    """流式过程中的一个事件。"""

    kind: Literal["content", "reasoning", "usage", "done"]
    text: str = ""
    result: LLMResult | None = None      # 仅 kind="usage" 时携带，由 _parse() 统一解析


class StreamError(LLMError):
    """流式过程中的错误。此时 HTTP 200 已经发出，无法再改状态码。"""


async def chat_stream(
    self,
    messages: list[dict[str, str]],
    *,
    temperature: float = 0.3,
    max_tokens: int | None = None,
    user_id: str | None = None,
    thinking: bool | None = None,
) -> AsyncIterator[StreamChunk]:
    """流式调用。**只在第一个 chunk 到达前可以重试**（见 §5.4）。"""
    thinking = settings.llm_thinking if thinking is None else thinking

    payload: dict = {
        "model": settings.llm_model,
        "messages": messages,
        "max_tokens": max_tokens or settings.llm_max_tokens,
        "stream": True,
        "thinking": {"type": "enabled" if thinking else "disabled"},
    }
    if thinking:
        payload["reasoning_effort"] = settings.llm_reasoning_effort
    else:
        payload["temperature"] = temperature
    if user_id:
        payload["user_id"] = user_id

    # 实测：DeepSeek 流式默认返回 usage，无需 stream_options（§1.1）
    usage: dict | None = None
    got_first_chunk = False
    start = time.perf_counter()

    async with self.client.stream("POST", "/chat/completions", json=payload) as resp:
        if resp.status_code != 200:
            body = (await resp.aread()).decode("utf-8", errors="replace")[:300]
            raise LLMError(
                f"LLM 流式请求失败 {resp.status_code}: {body}",
                status_code=resp.status_code,
                retryable=resp.status_code in RETRYABLE_STATUS,
            )

        async for line in resp.aiter_lines():
            # ★ 必须过滤：空行，以及 DeepSeek 的 SSE 保活注释 `: keep-alive`（§1.3）
            if not line.strip() or line.startswith(":"):
                continue
            if not line.startswith("data:"):
                continue

            data = line[5:].strip()
            if data == "[DONE]":                      # §1.2
                break

            try:
                obj = json.loads(data)
            except json.JSONDecodeError:
                logger.warning("无法解析的 SSE 数据行: %s", data[:120])
                continue

            if obj.get("usage"):                      # 最后一个 chunk 携带 usage
                usage = obj["usage"]

            for choice in obj.get("choices") or []:
                delta = choice.get("delta") or {}
                # ★ 思考模式的思维链必须单独分流，绝不能混进正文（§1.4）
                if delta.get("reasoning_content"):
                    yield StreamChunk(kind="reasoning", text=delta["reasoning_content"])
                if delta.get("content"):
                    got_first_chunk = True
                    yield StreamChunk(kind="content", text=delta["content"])

    # ★ 复用非流式的 _parse()，不在这里重复一遍 token 字段解析：
    #    缓存命中 token 字段名、reasoning_tokens、成本计算、高峰判定全都只有一处实现。
    #    代价是 content 字段对流式无意义（正文已经逐块发走了），只看 usage/cost/latency。
    result = self._parse(
        {"usage": usage or {}, "choices": [], "model": settings.llm_model}, start
    )
    yield StreamChunk(kind="usage", result=result)
    yield StreamChunk(kind="done")
```

### 5.2 流式下的重试：只能在第一个 chunk 之前

**这是流式与同步最大的工程差异**：

| | 同步 `chat()` | 流式 `chat_stream()` |
| --- | --- | --- |
| 失败时 | 可以安全重试最多 3 次 | **一旦有 chunk 推给客户端，就绝不能重试** |
| 原因 | 客户端还没收到任何东西 | 已经收到半句话，重试会导致**内容重复/错乱** |

所以流式的重试窗口只有："建立连接 + 首个 chunk 之前"：

```python
# 伪代码：外层包装
for attempt in range(1, settings.llm_max_retries + 1):
    try:
        async for chunk in chat_stream(...):
            got_first = True
            yield chunk
        break
    except LLMError as exc:
        if got_first or not exc.retryable:
            raise
        await asyncio.sleep(backoff(attempt))
```

**实践中更简单的做法**：流式**不做客户端重试**，只依赖 `LLMClient` 的连接超时。理由——用户已经盯着屏幕等了，重试带来的额外等待比"给个错误提示让用户重问"体验更差。本项目采用这个策略，并把 `LLM_STREAM_MAX_RETRIES` 默认设为 1（即不重试）。

### 5.3 SSE 事件协议

用**具名事件**（`event:` 字段），前端可以按类型分发：

```
event: meta
data: {"session_id": 12, "cache_hit": false}

event: reasoning
data: {"text": "用户在问退款"}

event: delta
data: {"text": "审核通过后，"}

event: delta
data: {"text": "款项将在 5-7 个工作日退回。"}

event: citations
data: {"citations": [{"document_id": 3, "chunk_id": 17, "seq": 0, ...}]}

event: done
data: {"usage": {"prompt_tokens": 199, "completion_tokens": 20, "cost_yuan": 0.000558,
                 "latency_ms": 869, "cache_hit": false}, "saved_cost_yuan": null}

```

**四个设计决定**：

1. **第一条必须是 `meta`**，带 `session_id`——前端要立刻知道会话 id 才能在后续请求里带上它。
2. **`reasoning` 单独成事件**：默认前端忽略它即可。这样"打开思考模式"不会污染正文。
3. **引用在正文结束后单独发**（`citations`），因为引用要等检索+生成完成后才能确定；混在 delta 里前端会很别扭。
4. **`done` 里带完整 usage**：让前端能显示本次耗时和花费。

**SSE 格式细节**（容易写错）：

```python
def sse_event(event: str, data: dict) -> str:
    """SSE 单条消息。注意：data 里不能有裸换行，否则会被解析成多条消息。"""
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\ndata: {payload}\n\n"      # 结尾必须是两个 \n
```

`json.dumps` 默认会把换行转义成 `\n`，所以安全。**但如果你手动拼字符串就会踩坑**——这是 SSE 最常见的 bug。

### 5.4 缓存命中时如何"假装流式"

命中缓存时答案是一整段文本。**不要一次性推完**，那样前端会感觉"卡了一下然后瞬间出现全文"，与流式的体验预期不符。

做法：按标点/固定长度切片，加极小延迟逐块推送：

```python
async def stream_cached_answer(text: str, chunk_size: int = 24) -> AsyncIterator[str]:
    """把缓存答案切块推送，模拟流式手感。

    要不要加 asyncio.sleep 是个产品决策：
    - 加：手感统一，但用户要多等
    - 不加：用户瞬间看到全文（其实更好，快就是快）
    本项目选择"不加延迟"，因为缓存的意义就是快 —— 快得明显，用户才知道系统在变快。
    """
    for i in range(0, len(text), chunk_size):
        yield text[i : i + chunk_size]
```

### 5.5 流式下的"边流边攒，结束后写缓存"

阶段 1 是"先查缓存 → 命中就返回"。流式下**新增一个难点**：

> 两个完全相同的请求几乎同时到达时，缓存里还没有答案（第一个请求正在生成），**两个都会打到 LLM**。这是"缓存击穿"。

三种处理，按复杂度排序：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **什么都不做**（本阶段选择） | 接受偶发的重复调用 | 实现最简；个人项目并发极低，实际损失可忽略 |
| Redis 分布式锁 | 用 `SET NX EX` 抢锁，抢不到就等待 | 需要处理"等多久""等不到怎么办"，且流式下等待体验差 |
| 单飞（singleflight） | 同一进程内相同请求合并 | 多 worker 下失效，收益有限 |

**明确记为技术债**：等真实并发上来（或成本明显被击穿浪费）再做。**现在做是过度设计。**

### 5.6 流式中的错误处理

HTTP 200 和 `text/event-stream` 头**一旦发出就无法更改**，所以流中途出错只能：

```python
async def _chat_event_source(db, llm, cache, user, payload):
    """SSE 事件源生成器：流中途出错时无法改 HTTP 状态码，只能发 error 事件。"""
    try:
        async for item in run_answer_stream(...):
            yield sse_event(...)
    except LLMError as exc:
        logger.error("流式生成中断: %s", exc)
        yield sse_event("error", {"code": 50201, "message": "AI 服务暂时不可用，请稍后重试"})
        yield sse_event("done", {"usage": None, "incomplete": True})
        return
```

**关键点**：
- 客户端**必须**处理 `event: error`，否则用户会看到半句话然后连接静默关闭
- 不能靠 HTTP 状态码传错误（已经 200 了）
- 已生成的部分内容**照常落库**（部分答案也有价值，且便于排障），但 `answer` 字段要标注未完成

### 6.2 流式端点

```python
# app/api/v1/endpoints/chat.py
from fastapi.responses import StreamingResponse

@router.post("", summary="问答（SSE 流式）")
async def chat_stream_endpoint(
    payload: ChatRequest,
    current_user: CurrentUser,
    db: DBSession,
    llm: LLMDep,
    cache: CacheDep,
) -> StreamingResponse:
    await check_rate_limit(cache, current_user.id)

    return StreamingResponse(
        _chat_event_source(db, llm, cache, current_user, payload),
        media_type="text/event-stream",
        headers={
            # 关掉所有缓冲，否则流会被攒起来一次性发出（代理/nginx 同理）
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",      # 给 nginx 看的
        },
    )
```

> **一个必须注意的坑**：`StreamingResponse` 的生成器里**不能直接 `await db.commit()` 后再依赖 `get_db` 的自动提交**——因为流式响应返回时，`get_db` 依赖的 `yield` 已经结束了。**必须在生成器内部自己提交事务**，否则落库静默失败（不报错，只是数据没进去）。
>
> 解法：生成器内部用独立的 session（`SessionLocal()` 直接开），不要依赖请求级 `db`。这是流式 + 依赖注入的经典冲突，**阶段 2 最容易踩的坑之一**。

### 6.3 同步端点复用同一套业务逻辑

`/chat/sync` 不应该重写一遍逻辑。把差异收在一处：

```python
async def run_answer(
    db, llm, cache, *, owner_id: int, question: str,
    session_id: int | None, top_k: int | None,
) -> tuple[str, list[RetrievedChunk], dict]:
    """非流式完整问答。逻辑与阶段 1 相同，只是加了会话。"""
    raise NotImplementedError


async def run_answer_stream(
    db, llm, cache, *, owner_id: int, question: str,
    session_id: int | None, top_k: int | None,
):
    """流式问答。命中缓存时走 stream_cached_answer；否则走 chat_stream。"""
    raise NotImplementedError
```

**测试策略因此可以复用**：验证业务逻辑时用 `/chat/sync`（JSON 好断言），只对 SSE 协议本身写少量专门的流式测试。**这是"两个端点都保留"这个决策带来的最大好处**——用户选的这个方案在测试成本上明显更优。

### 8.2 SSE 断言的工具函数

```python
def parse_sse(text: str) -> list[tuple[str, dict]]:
    """把 SSE 响应体解析成 [(event, data), ...]"""
    import json

    events: list[tuple[str, dict]] = []
    for block in text.strip().split("\n\n"):
        event, data = None, None
        for line in block.splitlines():
            if line.startswith("event:"):
                event = line[6:].strip()
            elif line.startswith("data:"):
                data = json.loads(line[5:].strip())
        if event:
            events.append((event, data))
    return events


async def test_stream_event_order(client, auth_headers):
    r = await client.post(
        "/api/v1/chat", headers=auth_headers, json={"question": "退款要多久？"}
    )
    assert r.headers["content-type"].startswith("text/event-stream")
    events = parse_sse(r.text)
    kinds = [e for e, _ in events]

    assert kinds[0] == "meta"                       # 首条必须是 meta
    assert kinds[-1] == "done"                      # 末条必须是 done
    assert "delta" in kinds                         # 中间有内容
    # 拼接 delta 应等于完整答案
    joined = "".join(d["text"] for e, d in events if e == "delta")
    assert joined
```

> **注意**：`httpx.ASGITransport` 会把整个流缓冲后一次性返回，所以测试里 `r.text` 能拿到完整 SSE 文本。**这简化了测试，但也意味着它测不出"是否真的逐块推送"**——真要验证这点得用真实网络或 `uvicorn` + `httpx` 实连。本阶段接受这个局限，在文档里记明。

## 10. 风险与取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **多轮下缓存命中率可能大幅下降** | 历史指纹让键更细，命中更难 | 这是**正确性的代价**，不能为了命中率牺牲正确性；用实测数据判断是否值得（实在不行可退回"只缓存首问"） |
| 缓存击穿（流式并发） | 相同请求同时到达会重复调 LLM | 已明确记为技术债（§5.5），并发上来再做 |
| 滑动窗口丢早期前提 | 用户说"我在测 A 系统"，6 轮后模型忘了 | 可接受；真有需要再加摘要（本次未选） |
| 流式下事务边界 | 生成器内不能用请求级 `db` | 生成器内自建 session 并自行 commit（§6.2） |
| SSE 无法用 HTTP 状态码报错 | 200 已发出 | 用 `event: error`，**客户端必须实现** |
| 测试测不出"真流式" | ASGITransport 会缓冲 | 记录局限；必要时用真实 uvicorn 实连做一次手工验证 |
